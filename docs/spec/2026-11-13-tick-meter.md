# ТЗ: периодический тик цикла событий и индикатор уровня `Meter`

- **Идентификатор:** `2026-11-13-tick-meter`
- **Дата:** 2026-11-13
- **Статус:** утверждено владельцем 2026-11-13 («1 - а; 2-4 по рекомендации; 05 половинками; 06 два»): О1–О4 — варианты (a); О5 — заполнение с точностью до половины ячейки (вариант владельца, см. §6); О6 — (a), два ADR. План — `docs/plans/2026-11-13-tick-meter.md`.
- **Постановка владельца (2026-11-13, проект `sfplayer`):** интерфейс `sf2_player` переводится на `gterm`; недостающее закрывается в самой библиотеке — «API периодического тика в цикле событий; универсальные виджеты (измеритель) — в gterm-widgets». Решение П-1 плана sfplayer (`docs/plans/2026-11-13-gterm-ui.md`, принято 2026-11-13): вернуть общий тик новым ADR поверх ADR-0012; мигание ячеек и остальное, убранное ADR-0012, не возвращается. Решение ОР-2 ТЗ sfplayer: измеритель — в `gterm-widgets`.
- **Основа:** ADR-0012 п.3 («Таймера в библиотеке нет … Цикл всегда ждёт событий») и отклонённая там альтернатива «общий периодический тик … приложение заведёт само»; ADR-0004, ADR-0006 (контракт `AppHandler`/`Ctx`/`Request`); ADR-0023, ADR-0032 (виджеты-значения, `Gauge`/`LineGauge`). Код: `crates/gterm/src/app/mod.rs:120` (`ControlFlow::Wait` — единственное место, где задаётся режим ожидания), `app/events.rs:11-107` (`ApplicationHandler` только с `resumed` и `window_event`), `app/events.rs:112-177` (`notify`/`apply_request`), `app/options.rs:79-91` (`AppOptions`), `app/api.rs:46-64` (`Request`), `crates/gterm-widgets/src/widgets/gauge.rs` (одноцветные `Gauge`/`LineGauge`).

## 1. Цель

1. Приложение на `gterm` может получать вызов с заданным периодом без пользовательского ввода — для индикаторов, таймеров, опроса своих потоков. Сейчас это невозможно: завести таймер «само» приложение не может, потому что разбудить цикл `winit` из другого потока нечем (`EventLoopProxy`, `about_to_wait`, `new_events` в `crates/` не используются), а единственный обходной путь — запрашивать кадр из `on_frame` — гонит кадры непрерывно.
2. В `gterm-widgets` есть индикатор уровня с цветовыми зонами и отметкой пика — то, чего не умеют `Gauge` и `LineGauge`.

## 2. Границы

**Входит — `crates/gterm`:**

1. **Период тика.** `AppOptions::tick_period: Option<Duration>` — начальное значение (по умолчанию `None`); `Request::tick_period: Option<Option<Duration>>` — смена на лету (`Some(None)` выключает) (О1). Период меньше 1 мс приводится к 1 мс.
2. **`AppHandler::on_tick(&mut self, ctx: &mut Ctx<'_>)`** с пустым телом по умолчанию. Вызывается на главном потоке тем же путём, что остальные обработчики (`notify` → `apply_request`): приложение может писать в экран, запрашивать кадр, выход, смену периода.
3. **Цикл.** Период задан — цикл ждёт до времени следующего тика (`ControlFlow::WaitUntil`); по наступлении времени — один вызов `on_tick`. Период не задан — прежний `ControlFlow::Wait`: в простое цикл не просыпается вообще (FR-26 сохраняется для приложений без тика).
4. **Отставание** (О2): пропущенные тики не догоняются — за одно пробуждение не больше одного `on_tick`, следующий назначается через период от момента текущего.
5. **Тик не запрашивает кадр** (О3): перерисовка — только по `ctx.redraw()` из обработчика.
6. До создания окна и после запроса выхода тики не приходят.
7. **Тест с окном** — отдельный бинарник `harness = false` на общем коде `tests/events_common/`, сценарии — запуском самого себя (как `stage8_faults`).

**Входит — `crates/gterm-widgets`:**

8. **`Meter`** (`src/widgets/meter.rs`, `pub use` в `widgets/mod.rs`) — виджет без состояния (`Widget`): горизонтальная полоса на всю область.
   - `ratio(f64)` — уровень 0…1 (вне отрезка обрезается, «не число» — ноль, как у `Gauge`);
   - `zones(&[(f64, Style)])` — пороги по возрастанию: зона действует от своего порога до следующего; без зон — один стиль `filled_style`;
   - цвет ячейки определяется **её положением** на шкале, а не текущим уровнем (О4): заполненная часть полосы многоцветна;
   - `peak(Option<f64>)` — отметка пика: одна целая ячейка символом `peak_symbol` в цвете своей зоны, рисуется и за пределами заполненной части (допущение агента: пик — целой ячейкой, половинная точность только у уровня);
   - `filled_symbol`, `half_symbol`, `unfilled_symbol`, `peak_symbol` (по умолчанию `█`, `▌`, `░`, `█`), `unfilled_style`, `style`, `block`;
   - заполнение — с точностью до половины ячейки (О5, решение владельца): целые ячейки — `filled_symbol`, половина — `half_symbol` (по умолчанию `▌`, левый полублок: рисуется процедурно и от шрифта не зависит), остальное — `unfilled_symbol`; правая половина «половинной» ячейки — фон `unfilled_style`.
9. **Пример** `widgets`: на вкладке индикаторов — `Meter` с тремя зонами и пиком.
10. **Тесты** без окна (`crates/gterm-widgets/tests/`): снимки строки для нескольких уровней, включая половинные, цвета ячеек по зонам через `cell().fg`, отметка пика внутри и вне заполненной части, обрезка значений и `NaN`, отсечение по области, отрисовка внутри `Block`, нулевая ширина.

**Документы:** ADR-0033 «Периодический тик приложения» (частично заменяет ADR-0012 п.3 и строку альтернатив о тике), ADR-0034 «Индикатор уровня `Meter`» (О6); ТЗ проекта (FR-26 и §13 — очередная версия); `AGENTS.md` (абзац состояния: «таймера в библиотеке нет, `on_tick` нет» → новая формулировка; список команд), `PROJECT_MAP.md`, `README.md` и `README.ru.md` (возможности), `TODO.md`, план и отчёты `docs/plans|done|test|verify/`, размеры release.

**Не входит:**

- мигание ячеек, `BLINK`, `Ctx::blink_phase`, фаза в шейдере — ADR-0012 в этой части остаётся в силе;
- пробуждение цикла из другого потока (`EventLoopProxy`, пользовательские события);
- несколько независимых таймеров, одноразовые таймеры;
- таймеры у виджетов: `Control::tick` и `Ui::tick` не меняются, повтор полосы прокрутки по-прежнему ведёт `on_frame` (приложение вправе звать `Ui::tick` из `on_tick`);
- состояние наведения у контролов, выпадающие подсказки у `TextInput`, отрисовка вложенных слоёв, минимальный размер окна — в `sfplayer` решено обойтись без них (П-2, П-4 его плана);
- удержание пика во времени и спад уровня в `Meter` — значения считает приложение.

## 3. Контракты

- Без заданного периода поведение библиотеки не меняется: цикл в `Wait`, `on_tick` не вызывается, существующие приложения и тесты не затронуты.
- `on_tick` приходит не раньше назначенного времени; между двумя вызовами проходит не меньше периода (с точностью системного таймера). Верхней гарантии нет: долгий обработчик или кадр задерживают тик, пропущенные не догоняются.
- Смена периода из любого обработчика действует со следующего ожидания: новый отсчёт — от момента применения запроса.
- Тик и события ввода не вложены друг в друга: обработчики вызываются по одному.
- `Meter` ничего не хранит между кадрами и не выделяет память при отрисовке сверх того, что делает `Gauge`.
- Публичные перечисления не расширяются; `AppOptions` и `Request` получают по одному полю — внешний код, создающий `AppOptions` литералом без `..Default::default()`, перестанет собираться (в репозитории такие места правятся в этой задаче).

## 4. Критерии приёмки

| № | Критерий | Чем подтверждается |
|---|---|---|
| К1 | С периодом из `AppOptions` приходят тики: за время теста — ожидаемое число в допуске, интервалы не короче периода | оконный тест-бинарник |
| К2 | Без периода тиков нет; цикл в простое не просыпается | оконный тест: счётчик тиков ноль за контрольное время; чтение кода (`Wait` при `None`) |
| К3 | Смена и выключение периода через `Request` действуют | оконный тест |
| К4 | Тик без `ctx.redraw()` кадра не вызывает; с ним — вызывает | оконный тест по `FrameStats::frames` |
| К5 | Отставание не догоняется: после задержки в обработчике приходит один тик, не серия | оконный тест |
| К6 | `Meter`: заполнение по уровню с шагом в половину ячейки, цвета ячеек по зонам, символы и стили | тесты по снимкам |
| К7 | `Meter`: пик внутри и вне заполненной части, в цвете своей зоны | тесты по снимкам |
| К8 | `Meter`: значения вне 0…1 и `NaN`, обрезка по области, нулевая ширина, внутри `Block` | тесты без окна |
| К9 | Пример `widgets` показывает `Meter` | сборка; снимок окна `tools/shot.ps1`; глазами — владелец |
| К10 | Гейты, размеры release, документы | `fmt`, `clippy --all-targets -D warnings`, `cargo test`; размеры; ADR-0033, ADR-0034, документы, отчёты |

## 5. Риски

- **Отмена решения ADR-0012.** Таймер убирали вместе с миганием; возвращается только общий тик, но FR-26 («в простое цикл не просыпается») теперь выполняется лишь для приложений без периода — формулировку ТЗ проекта нужно привести к этому.
- **Точность.** `WaitUntil` на Windows зависит от разрешения системного таймера (обычно до ~15 мс); К1 проверяется с допуском, жёсткая периодичность не обещается.
- **Оконные тесты** дольше остальных и зависят от машины: допуски по числу тиков выбираются широкими, сторож с тайм-аутом — как в существующих бинарниках.
- **Linux/Wayland:** поведение `WaitUntil` там не проверяется автоматически (хост разработки — Windows); проверка — владельцем.

## 6. Открытые вопросы — приняты владельцем 2026-11-13: О1 (a), О2 (a), О3 (a), О4 (a), О5 — половинками, О6 (a)

- **О1. Где задаётся период.** (a) **Рекомендуется:** начальное значение в `AppOptions::tick_period` и смена на лету в `Request::tick_period` — так было до ADR-0012 (`blink_period`), и так устроены остальные параметры цикла; (b) только `Request` — приложение включает тик из первого же обработчика (`on_backend_changed`), `AppOptions` не меняется.
- **О2. Отставание.** (a) **Рекомендуется:** не догонять — один `on_tick` за пробуждение, следующий через период от текущего момента: индикаторам нужен «свежий» вызов, а не серия; (b) держать сетку времени — следующий тик через период от *назначенного* времени предыдущего, с пропуском уже прошедших; средняя частота точнее, интервалы неравномерны.
- **О3. Кадр по тику.** (a) **Рекомендуется:** тик кадр не запрашивает — приложение решает само (`ctx.redraw()`), в простое без изменений экран не перерисовывается; (b) каждый тик запрашивает кадр.
- **О4. Цвет заполненной части `Meter`.** (a) **Рекомендуется:** по положению ячейки — полоса многоцветна (зелёная, затем янтарная, затем красная), как у измерителей уровня; (b) по текущему уровню — вся заполненная часть одного цвета зоны, в которую попал уровень; (c) оба режима переключателем.
- **О5. Точность заполнения `Meter`.** (a) **Рекомендуется:** целыми ячейками с символами заполненной и пустой части (`█`/`░`) — дробная ячейка несовместима с символом пустой части в той же ячейке; (b) восьмушками, как `Gauge`, с фоном вместо символа пустой части; (c) оба режима переключателем `use_unicode`. **Решение владельца:** ни один из трёх — точность в половину ячейки: полублок `▌` для дробной ячейки при сохранении символа пустой части в остальных.
- **О6. ADR.** (a) **Рекомендуется:** два — 0033 (тик, частично заменяет 0012) и 0034 (`Meter`): решения независимы и в разных крейтах; (b) один общий ADR на задачу.
