# ТЗ: комбинации клавиш — структура, запись в строку и разбор из строки, модуль `gterm::hotkey`

- **Идентификатор:** `2026-10-30-hotkeys`
- **Дата:** 2026-10-30
- **Статус:** утверждено владельцем 2026-10-30 («Да, так»: О1 — цепочка удержанных включая отпускаемую, О2 — повтор записывается как есть, О3 — трекер автотестом, окно глазами). План — `docs/plans/2026-10-30-hotkeys.md`, решения — ADR-0028.
- **Постановка владельца (2026-10-30):** отдельная структура комбинации клавиш: создаётся при нажатии первой клавиши, живёт, пока хоть одна нажата, уничтожается при отпускании всех. Поля `fullHotkey` (вся история нажатий за время жизни) и `currentHotkey` (что нажато сейчас). Сигнал — на каждое отпускание клавиши, одно поле `hotkey`; при отпускании всех клавиш присылается полная комбинация. Клавиши не зависят от раскладки: `Ctrl+K` срабатывает и на кириллической «Л» — запись всегда модификаторами, латинскими буквами и именами знаков. Запись: `Ctrl+K`; `Ctrl+[K,U]` — при нажатом Ctrl нажата K, отпущена, нажата U; `Space+[Ctrl+[K,U]]` — вложенное удержание; `K|U` — «K или U» (образец). Решения 2026-10-30: модуль `hotkey` в `gterm`; `on_key` получает и отпускания; имена знаков — по кодам `winit` (`Comma`, `BracketLeft`, …), без экранирования.
- **Основа:** ADR-0004 (библиотека ввод не интерпретирует — структуру кормит приложение), ADR-0026/0027 (`KeyMsg`, `Ui::key` в `gterm-widgets`); код `crates/gterm/src/app/events.rs:38` (сейчас в `on_key` проходят только `Pressed`), `app/api.rs:137` (документация `on_key` — «нажатие или отпускание»); `winit 0.30.13`: `KeyEvent.physical_key: PhysicalKey::Code(KeyCode)` — раскладко-независимый код клавиши с именами по US-раскладке (`KeyK`, `ControlLeft`, `BracketLeft`, `Comma`, `Digit1`, `F1`, `Space`, `ArrowUp`, `NumpadAdd`), `KeyEvent.repeat` — автоповтор; обработчики `on_key` всех бинарников и примеров уже проверяют `state == Pressed`.

## 1. Цель

Приложение получает из потока нажатий и отпусканий структуру комбинации клавиш, не зависящую от раскладки, с однозначной текстовой записью в обе стороны (`Display`/`FromStr`) и сопоставлением с образцами (включая `K|U`). На ней дальше строятся карты «сочетание → действие» в приложениях и, отдельной задачей, в `gterm-widgets`.

## 2. Границы

**Входит — `crates/gterm`, новый модуль `src/hotkey.rs` (без окна и без `unsafe`, зависит только от типов `winit::keyboard`):**

1. **Клавиша `Key`** — раскладко-независимая: модификаторы `Ctrl`, `Alt`, `Shift`, `Super` (левый и правый не различаются: `ControlLeft`/`ControlRight` → `Ctrl`) и прочие клавиши по `KeyCode` (`Key::Code(KeyCode)`). Из события — `Key::from_event(&KeyEvent) -> Option<Key>` по `physical_key`; `PhysicalKey::Unidentified` → `None` (событие не учитывается). `Key::is_modifier()`.
2. **Имена** (`Display`/разбор, регистр букв в записи не важен, канонический вид — как ниже): модификаторы `Ctrl`, `Alt`, `Shift`, `Super`; буквы `A`–`Z` (`KeyA`…), цифры `0`–`9` (`Digit0`…), `F1`–`F24`; `Space`, `Enter`, `Esc`, `Tab`, `Backspace`, `Delete`, `Insert`, `Home`, `End`, `PageUp`, `PageDown`, `Up`, `Down`, `Left`, `Right`; знаки по кодам `winit`: `Comma`, `Period`, `Minus`, `Equal`, `BracketLeft`, `BracketRight`, `Semicolon`, `Quote`, `Backquote`, `Slash`, `Backslash`, `IntlBackslash`; остальные коды — имя варианта `KeyCode` как есть (`NumpadAdd`, `CapsLock`, `ContextMenu`, `MediaPlayPause` …), разбор принимает их же. Имя занимает ровно одну лексему: `+ , [ ] |` и пробелы — грамматика.
3. **Структура `Hotkey`** — дерево удержаний: последовательность узлов; узел — клавиша и вложенная последовательность того, что нажималось, пока она была удержана. Инварианты записи: узел без вложений — `K`; с одним вложенным узлом — `K+inner`; с несколькими — `K+[a,b]`; последовательность на верхнем уровне — `a,b`. Примеры: `Ctrl+K`; `Ctrl+[K,U]`; `Space+[Ctrl+[K,U]]`; `K,U` (K нажата и отпущена, затем U); `Ctrl+Shift+K` (Shift нажат при удержанном Ctrl, затем K). **Модификаторы, удержанные одновременно, — множество:** при записи и сравнении подряд идущие удержания модификаторов приводятся к каноническому порядку `Ctrl`, `Alt`, `Shift`, `Super` (`Shift+Ctrl+K` ≡ `Ctrl+Shift+K`); порядок прочих клавиш значим. Методы: `Display` (канонический вид), `FromStr` (`ParseError { position, kind }`: неизвестное имя, пустой элемент, лишняя/незакрытая скобка, `|` вне образца), `is_empty`, `keys()`. Образец `K|U`: альтернативы на любом уровне (`Ctrl+[K|U]`, `Ctrl+S|Super+S`), только в разборе и сравнении — записанная комбинация альтернатив не содержит; `Hotkey::matches(&self, pattern: &Hotkey) -> bool` — структурное совпадение с учётом альтернатив и канонизации модификаторов. Круговое свойство: `parse(x).to_string()` даёт канонический вид, `parse(canonical) == parse(x)`.
4. **Трекер `HotkeyTracker`** — состояние между событиями: `full: Hotkey` (история с первого нажатия), `held: Vec<Key>` (нажатые сейчас в порядке нажатия; `current()` — их цепочка как `Hotkey`: `Ctrl+U`), `feed(&KeyEvent) -> Option<HotkeyEvent>`; автоповтор (`repeat`) и `Unidentified` игнорируются; нажатие уже удержанной клавиши игнорируется; отпускание клавиши, которой нет в `held` (нажата до старта приложения или потеряна при уходе фокуса окна), игнорируется. Нажатие: если `held` пуст — новая жизнь (`full` очищен), узел добавляется в конец последовательности самого глубокого удержанного узла (или на верхний уровень). Отпускание: клавиша убирается из `held`; **сигнал `HotkeyEvent { hotkey: Hotkey, complete: bool }`** — на каждое отпускание: `hotkey` = цепочка удержанных клавиш на момент перед отпусканием (`current` включая отпускаемую: отпустили K при Ctrl → `Ctrl+K`), `complete = false`; когда отпущена последняя — `hotkey = full`, `complete = true`, трекер пуст. Пример владельца: Ctrl↓ K↓ (`full` `Ctrl+K`, `current` `Ctrl+K`) K↑ → сигнал `Ctrl+K`; U↓ (`full` `Ctrl+[K,U]`, `current` `Ctrl+U`); Ctrl↑ → сигнал `Ctrl+U`, `current` `U`; U↑ → сигнал `Ctrl+[K,U]`, `complete`. `reset()` — сброс (например, при потере фокуса окна). Приложение кормит трекер из `AppHandler::on_key` обоими состояниями.
5. **`gterm`, доставка отпусканий:** `events.rs` — `KeyboardInput` без фильтра по `Pressed`: `on_key` получает `Pressed` и `Released` (как и обещает документация). Все бинарники и примеры уже проверяют состояние; `gterm-widgets`: `Ui::key` пропускает только `Pressed` (`Released` → `Routed::ignored()`), остальное без изменений.
6. **Пример** `crates/gterm/examples/hotkeys.rs` (системный шрифт, как `minimal`): три строки — «нажато сейчас» (`current`), «полная» (`full` живой комбинации), «последняя завершённая» (`hotkey` последнего `complete`) и журнал последних сигналов (`hotkey`, `complete`); карта образцов из строк (`Ctrl+S` → «сохранить», `Ctrl+[K,U]` → «аккорд», `K|U` → «K или U», `Space+[Ctrl+[K,U]]`) — при каждом сигнале показывается, какие образцы совпали (`matches`); `Esc` — выход, когда ничего не удержано. Проверка раскладки — глазами: `Ctrl+K` совпадает в русской раскладке.
7. **Тесты** `crates/gterm/tests/hotkey.rs` без окна (`KeyEvent` сконструировать нельзя — трекер принимает `(Key, ElementState, repeat)` через `feed_key`, а `feed(&KeyEvent)` — тонкая обёртка): разбор и запись (все примеры постановки, канонизация модификаторов, круговое свойство, ошибки с позициями), `matches` (альтернативы на разных уровнях, порядок прочих клавиш значим, модификаторы — нет), трекер по сценарию владельца шаг за шагом (`full`, `current`, сигналы), сценарий `Space+[Ctrl+[K,U]]`, автоповтор и повторное нажатие игнорируются, отпускание неизвестной клавиши игнорируется, `reset`; `Key::from_event` — имена для букв, цифр, знаков, модификаторов (левый/правый). `gterm-widgets`: фильтр `Released` в `Ui::key` автотестом не покрывается — `KeyEvent` без окна не сконструировать, а ввод оконные тесты не инжектируют (О3); проверка — чтением кода в `docs/verify` и глазами в примерах виджетов.
8. **Документы:** ADR-0028 (структура и запись комбинаций, доставка отпусканий), ТЗ 1.23 (§13, FR-25), `AGENTS.md`, `PROJECT_MAP.md`, `TODO.md` (пункт «комбинации клавиш» закрывается в части структуры и записи; карта «сочетание → сообщение» в `gterm-widgets` остаётся), отчёты `docs/done|test|verify/`; размеры release (`demo.exe`, `hotkeys.exe`).

**Не входит:**

- карта «сочетание → действие/сообщение» в `gterm-widgets` и перехват комбинаций деревом `Ui` — следующая задача на этой структуре;
- различение левых/правых модификаторов, `AltGr`, клавиши мыши в комбинациях, тайм-ауты между нажатиями аккорда;
- запись по логическим клавишам (`Key::Character`) и локализация имён;
- изменения рендереров; новые зависимости.

## 3. Контракты

- `Key` строится только из `physical_key`: одна и та же физическая клавиша даёт одну `Key` в любой раскладке.
- `Hotkey`: `to_string()` всегда разбирается обратно в равную структуру; две записи, различающиеся только порядком подряд идущих модификаторов, равны; порядок прочих клавиш и вложенность значимы.
- `matches`: образец без `|` совпадает только с равной структурой; `a|b` совпадает, если совпадает `a` или `b`; записанная комбинация (`full`, `current`, `hotkey` сигнала) не содержит `|`.
- Трекер: `held` непуст тогда и только тогда, когда комбинация жива; после `complete` трекер пуст; сигнал ровно один на каждое учтённое отпускание; автоповтор, повторные нажатия и чужие отпускания ничего не меняют.
- `on_key` получает `Pressed` и `Released`; поведение всех существующих обработчиков не меняется (они проверяют состояние); `Ui::key` на `Released` возвращает `Routed::ignored()` без доставки.
- Модуль без `unsafe` и без выделений в `feed` сверх роста `full`/`held` (строки строятся только в `Display`).

## 5. Риски

- Отпускание клавиши, нажатой до появления окна или ушедшей вместе с фокусом окна (Alt+Tab): `held` рассинхронизируется — чужие отпускания игнорируются, а «зависшую» клавишу снимает `reset()`; приложение вызывает его, когда считает нужным (в примере — по `Esc`, когда комбинация пуста). Потери фокуса окна библиотека не сообщает (не в этой задаче).
- `KeyCode` в `winit` — нестабильное по составу перечисление; имена для редких клавиш берутся из `Debug`, и при смене версии `winit` запись таких клавиш может измениться. Частые клавиши зафиксированы собственной таблицей.
- Сигнал на отпускание Ctrl при удержанной U даёт `Ctrl+U` — такой же, как при отпускании U при удержанном Ctrl: приложение различает их только порядком в `full`. Осознанно: `hotkey` сигнала — цепочка удержанных, а не история.
- `Hotkey` содержит `Vec` — строится в обработчике событий, не в кадре; NFR-6 не затронут.

## 6. Открытые вопросы

- **О1. Содержимое `hotkey` в сигнале на частичное отпускание.** (a) **Рекомендуется (принято в п. 4 по постановке):** цепочка удержанных клавиш на момент перед отпусканием, включая отпускаемую (`Ctrl+K`); (b) история с начала жизни до этого момента (`full` на текущий момент: после Ctrl↑ при удержанной U — `Ctrl+[K,U]`); (c) только отпущенная клавиша.
- **О2. Повторное нажатие той же клавиши в одной жизни** (Ctrl↓ K↓ K↑ K↓ K↑ Ctrl↑). (a) **Рекомендуется:** записывается как есть — `Ctrl+[K,K]`; (b) схлопывать в `Ctrl+K`.
- **О3. Проверка доставки отпусканий автотестом.** Оконные тесты не инжектируют ввод, `KeyEvent` без окна не сконструировать. (a) **Рекомендуется:** автотест на уровне трекера через `feed_key` и проверка `events.rs` чтением кода в `docs/verify`, поведение на окне — глазами в примере (К6); (b) добавить в `events_common::Probe` счётчик состояний `on_key` — без ввода он останется нулём и ничего не докажет.
