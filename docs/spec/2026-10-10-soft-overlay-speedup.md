# ТЗ: ускорение наложения в Software-рендерере

- **Идентификатор:** `2026-10-10-soft-overlay-speedup`
- **Дата:** 2026-10-10
- **Статус:** утверждено владельцем 2026-10-10 (О1 — а)
- **Основа:** ADR-0014 (наложение клиентских буферов), минусы: «Software с полупрозрачным наложением на весь экран — 23,6 FPS при NFR-5 ≥ 60… Ускорение — отдельная задача».
- **Решение владельца (2026-10-10):** порядок работ 0 → 1 → 2: замер разбивки, кэш текстуры наложения, два канала на одно умножение.

## 1. Цель

Снизить цену наложения в Software, не меняя результат кадра ни на бит. Бит-идентичность с GL и golden-эталоны сохраняются.

## 2. Исходный замер (шаг 0, сделан 2026-10-10)

`demo --bench --backend=soft --overlay`, release, сетка 120×40. Таймеры стояли в копии крейта вне репозитория; среднее по 330 кадрам:

| Фаза кадра | мс |
|---|---|
| Основной слой (`draw_row` по всем строкам) | 8,8 |
| Сборка текстуры наложения (очистка + `draw_overlay_cell`) | 21,0 |
| Наложение текстуры на кадр (`composite_row`) | 10,6 |
| **Итого** | ≈ 40,4 (23,8 FPS) |

Без наложения в той же сборке: основной слой 8,9 мс, 99 FPS.

## 3. Границы

**Входит:**
1. **Кэш текстуры наложения.** Если записи кадра (ячейки, позиции, размеры, порядок) совпадают с записями прошлого кадра, а геометрия текстуры не менялась, текстура не пересобирается. Наложение на кадр выполняется как обычно.
2. **Два канала на одно умножение (SWAR).** В `blend`, `over`, `composite` каналы R и B считаются одним 32-битным умножением и одним `div255` по двум 16-битным половинам. Формулы ADR-0002 / ADR-0013 / ADR-0014 не меняются, результат тот же бит в бит.
3. Тесты, замер `--bench` с наложением и без, ADR-0015.

**Не входит:**
- пропуск перерисовки строк под неизменным наложением и под непрозрачными ячейками наложения (пункты 3–4 обсуждения 2026-10-09) — отдельная задача;
- GL-бэкенд: его CPU-часть кадра с наложением (1,24 мс) не трогаем;
- профиль `opt-level` (§10.2) и многопоточность;
- изменения публичного API.

## 4. Контракты

- Публичный API (`AppHandler`, `DrawCtx`, `Overlay`, `Renderer`) не меняется.
- Кадр Software после задачи бит в бит равен кадру до задачи при любой последовательности кадров: с наложением и без, при смене записей, позиции, размера окна, DPI, фона буфера, при сбросе атласа.
- NFR-6: после первого кадра того же размера выделений памяти в кадре нет, включая копию записей прошлого кадра.

## 5. Критерии приёмки

| № | Критерий | Чем подтверждается |
|---|---|---|
| К1 | Кадры бит-идентичны прежним | `stage3_render golden`, `stage4_gl` (GL ↔ Software, допуск 0), `tests/overlay.rs`, `soft_partial_redraw` — зелёные без правки эталонов |
| К2 | Кэш не отдаёт устаревшую текстуру | новые тесты: та же запись при меняющемся основном экране; смена содержимого записи при той же позиции; смена позиции; исчезновение и возврат записи; смена размера окна и DPI — кадр равен кадру с нуля |
| К3 | SWAR-функции равны эталонным формулам | тест перебором всех входов по каналу (как у `div255`) |
| К4 | Без наложения не медленнее | `--bench --backend=soft`: не ниже 99–103 FPS (разброс замера) |
| К5 | Наложение быстрее | `--bench --backend=soft --overlay`: FPS выше 23,8; цифра и разбивка — в отчёте. NFR-5 (≥ 60) — цель, не критерий приёмки; если не достигнута — ⚠ в отчёте |
| К6 | Нет выделений памяти после первого кадра | тест ёмкости по образцу `repeated_frame_does_not_grow_memory` |
| К7 | Гейты | `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` |
| К8 | Размер бинарника замерен (NFR-1) | отчёт |
