## Контракт флагов

| Флаг | Поле `Config` | Поведение |
|---|---|---|
| `--fail-frames=N` | `fail_frames: u32`, по умолчанию 0 | первые `N` попыток кадра за запуск завершаются `RenderError::Other("injected by --fail-frames")`; счётчик общий — повторы и кадры после отката считаются |
| `--lose-context` | `lose_context: bool`, по умолчанию `false` | первая попытка кадра завершается `RenderError::ContextLost`, один раз |

- `--fail-frames` без значения → `ConfigError::MissingValue`; не число → новый вариант `ConfigError::BadNumber { option, value }`.
- Точка инжекции — `App::render_frame`, после настоящего рендера и вывода, до обновления `FrameStats`: ошибочный кадр в статистику не попадает (как сейчас), `on_frame` за него не приходит.
- Горячий путь: сравнение счётчика и флага, без аллокаций; строка ошибки создаётся только при инжекции.

Ожидаемое поведение (следует из `redraw`, тест это и проверяет):

| Запуск | Ожидание |
|---|---|
| `--fail-frames=1` | один повтор, бэкенд не меняется |
| `--fail-frames=2` на GL | повтор, затем откат на Software, работа продолжается |
| `--lose-context` на GL | откат на Software сразу, без повтора |
| `--backend=soft --fail-frames=2` | повтор, затем остановка: `App::run` возвращает `AppError::Render` |
| `--fail-frames=4` на GL | откат на Software, затем остановка с `AppError::Render` |

## Проектные решения плана (вето владельца — до утверждения)

1. **Один тест-бинарник, перезапускающий сам себя.** `winit` разрешает один цикл событий на процесс, сценариев пять. Вместо пяти целей Cargo — один `stage8_faults` (`harness = false`): без аргументов он запускает себя же (`std::env::current_exe`) по разу на сценарий и проверяет код возврата и stderr дочернего процесса; с аргументом — исполняет один сценарий на окне. Правило `AGENTS.md` «один цикл на процесс, общий код в `tests/events_common/`» соблюдается. Дополнительная польза: проверяется текст stderr (`retrying once`, `switching to Software` — FR-20).
2. **Пропуски.** Нет цикла событий → сценарий печатает причину и завершается успешно (как остальные оконные тесты). Сценарии «на GL» при старте сразу на Software (GL недоступен) печатают причину и пропускаются — как `stage4_gl`; сценарии повтора и остановки на Software от GL не зависят и выполняются всегда.

## Риски

- **Тест найдёт дефект политики** (например, кадр после повтора или отката неполный). Исправление — вне рамок этого плана: остановка и вопрос владельцу.
- **Содержимое кадра в оконном тесте не читается** — проверяются последовательность бэкендов, счётчики кадров, результат `App::run` и stderr; попиксельная идентичность после отката уже покрыта `stage4_gl` и `stage6_app` на уровне рендереров.
- **Порядок строк stderr дочернего процесса** проверяется по вхождению подстрок, а не по точному тексту целиком — сообщения драйвера могут добавлять свои строки.
