## Факты по коду (проверено 2026-10-08)

- `SoftBackend::render` (`src/renderer/soft_backend.rs:208-248`) уже рисует только dirty-строки. Полный кадр — при `needs_full_redraw` (первый кадр, `resize`, `set_size`), сбросе атласа или **любом** изменении `ViewParams` (`last_view != Some(*view)`, строка 219). `ViewParams` = `{ border_color, blink_phase }`.
- `App::render_frame` (`src/app.rs:725`) перед каждым кадром ставит `view.blink_phase = blink.visible(now)`. Смена фазы (2 раза в секунду при периоде 500 мс) → полная перерисовка всего окна. Замер этапа 6 (Linux, окно 2194×1234): **Software с миганием — 2,60 % CPU**, без мигания 0,00 %; GL с миганием 0,20 %.
- Вывод кадра (`src/app.rs:737-747`): `surface.buffer_mut()` → `buffer.copy_from_slice(frame)` (**весь кадр**) → `buffer.present()` (**весь кадр**), даже если перерисована одна строка или ничего.
- `ScreenBuffer` хранит только общее число `BLINK`-ячеек (`blink_count`, `src/buffer.rs:19`) — для таймера (FR-26); построчного учёта нет.
- `softbuffer 0.4.8` умеет:
  - `Buffer::age()` — 0: содержимое не определено (новый буфер, после `resize`); 1: буфер хранит прошлый кадр; 2: позапрошлый. Win32 (`backends/win32.rs:308`) и X11 (`x11.rs:416`) — один буфер, после первого вывода `age = 1`. Wayland (`wayland/mod.rs:293`) — двойная/тройная буферизация, `age` бывает 2.
  - `Buffer::present_with_damage(&[Rect])` — Win32 (`BitBlt` только прямоугольников), X11 с XShm, Wayland; на прочих — как `present()`.
- GL-бэкенд не затрагивается: кадр — один draw call по всей текстуре данных, смена фазы — uniform, в текстуру грузятся только dirty-строки уже сейчас.

## Решения (AR-04) — закрыты 2026-10-08: 1а, 2а, 3а, 4а, 5а

1. **Где узнавать строки с `BLINK` (пункт А).**
   - (а) **Рендерер сам** при смене только `blink_phase` проходит по ячейкам и перерисовывает строки, где есть `BLINK`. Буфер не меняется; проход 80×25 = 2000 ячеек два раза в секунду ничтожен против перерисовки 2,2 Мпикс. *Рекомендую — минимальный дифф.*
   - (б) Построчные счётчики `BLINK` в `ScreenBuffer` (`row_has_blinking(row)`), поддерживаемые в `put`/`recount` наравне с `blink_count`. Быстрее на огромных сетках, но больше инвариантов в буфере и правка его публичного API.
2. **Единица «изменённой части» (пункт Б).**
   - (а) **Полосы строк сетки**: перерисованная строка → прямоугольник `origin_x…origin_x + ширина сетки` × высота ячейки; соседние строки сливаются в одну полосу. Совпадает с единицей перерисовки. *Рекомендую.*
   - (б) Точные прямоугольники изменённых ячеек — меньше пикселей в редких случаях, но нужен учёт ячеек, а не строк (`ScreenBuffer` его не ведёт).
3. **Буфер окна не хранит прошлый кадр (`age ≠ 1`: первый кадр, после `resize`, Wayland с `age = 2`).**
   - (а) **Копировать весь кадр и `present()` целиком** — всегда корректно; на Wayland выигрыш только от пункта А. *Рекомендую на этом этапе.*
   - (б) Помнить полосы прошлого кадра и при `age = 2` копировать объединение двух — выигрыш и на Wayland, но больше состояния и случаев.
4. **Перерисовка по запросу системы.** На X11 без композитора открытое заново окно (было перекрыто) приходит как `RedrawRequested`; если вывести только «изменённые» полосы, открытая часть окна останется мусорной. Win32 с DWM содержимое окна хранит сам.
   - (а) **Отличать свои запросы от системных**: `App` помечает кадр, запрошенный приложением/таймером; `RedrawRequested` без пометки → полный вывод (весь кадр, `present()`). *Рекомендую.*
   - (б) Всегда полный `present()` (только копирование частичное) — проще, но на Win32 теряется половина выигрыша Б.
5. **Нечего выводить** (кадр запрошен, но ни одна строка не перерисована — например, тик статуса без изменений).
   - (а) **Не трогать буфер окна и не вызывать `present`** вовсе. *Рекомендую* — но только для своих запросов (см. решение 4).
   - (б) Как сейчас — полный вывод.

## Проектные решения (в ADR-0010 после утверждения)

- `SoftBackend` после `render` отдаёт **полосы перерисовки** кадра: `damage() -> &[RowBand]`, `RowBand { y, height }` в пикселях кадра, соседние строки слиты; при полном кадре — одна полоса на всю высоту. Буфер полос предвыделен и переиспользуется (NFR-6).
- Смена только `blink_phase` (тот же `border_color`, нет иных причин полного кадра) → перерисовываются строки с `BLINK` (решение 1) плюс обычные dirty-строки. Смена `border_color` — по-прежнему полный кадр.
- `App::render_frame`, ветка Software: `age() == 1` и кадр не системный → копируются только строки полос из `frame()` в буфер окна, вывод `present_with_damage(&rects)`; иначе — как сейчас (весь кадр, `present()`). Перевод полосы в `softbuffer::Rect` с обрезкой по окну — чистая функция, тестируется отдельно.
- **Инвариант, который проверяют тесты:** кадр после любой последовательности частичных перерисовок **бит-идентичен** кадру, нарисованному с нуля для того же экрана и вида. Это то же требование, что держит GL ↔ Software (§11.2).

## Риски

- **Мусор на экране при неверном учёте полос** — главный риск: ошибка не видна тестам кадра (кадр рендерера правильный), видна только в окне. Смягчение: чистая функция полос → `Rect` под тестами, системные перерисовки — полным выводом (решение 4), проверка глазами на Windows и Linux X11/Wayland (§11.3).
- **Wayland и `age = 2`** при решении 3а — корректно, но без выигрыша Б; замер на Linux — у владельца.
- **Выигрыш пункта Б на Windows может оказаться небольшим**: `BitBlt` всего окна дешевле перерисовки, основная цена — сама перерисовка (пункт А). Оценка — по замеру шага 6, а не по ожиданию (CQ-10.4).
- **Замер этапа 6 был на Linux**, этот — на Windows: сравнение «до/после» только в пределах одной машины.
