# ADR-0015. Software: кэш текстуры наложения и пары каналов в одном умножении

- **Дата:** 2026-10-10
- **Статус:** Accepted (дополняет ADR-0014 п.5 и п.7)
- **Тема:** NFR-5, NFR-6, §8. ТЗ задачи — `docs/spec/2026-10-10-soft-overlay-speedup.md`, план — `docs/plans/2026-10-10-soft-overlay-speedup.md`.

## Контекст

ADR-0014 оставил минус: Software с полупрозрачным наложением на весь экран — 23,6 FPS при NFR-5 ≥ 60. Замер по фазам кадра (`--bench --backend=soft --overlay`, 120×40, release):

| Фаза | мс |
|---|---|
| основной слой | 8,8 |
| сборка текстуры наложения | 21,0 |
| наложение текстуры на кадр | 10,6 |

Текстура собиралась заново каждый кадр, хотя клиент чаще всего рисует то же самое: неподвижное окно, меню, подсветку. Решение владельца (2026-10-10): порядок «замер → кэш текстуры → пары каналов», О1 — а (сравнение записей внутри `SoftBackend`, API не меняется).

## Решение

1. **Кэш текстуры наложения.**
   - `SoftBackend` хранит копию записей, по которым собрана текстура (`overlay_drawn`), и признак `is_overlay_valid`.
   - Текстура пересобирается, если записи кадра отличаются от `overlay_drawn` (ячейки, позиции, размеры, порядок), если изменился размер сетки в пикселях или если сменились метрики ячейки (`set_size`, смена DPI). В последнем случае текстура очищается целиком: при пересчёте сетки в `AutoGrid` размер в пикселях может совпасть, а растр глифов уже другой.
   - Иначе текстура только накладывается на перерисованные строки. Правило ADR-0014 «строки под наложением в этом и прошлом кадре перерисовываются всегда» не меняется.
   - `Overlay`: `PartialEq`; `Clone::clone_from` переиспользует память приёмника, поэтому копия записей не выделяет память после первого кадра (NFR-6).
2. **Пары каналов в одном умножении (SWAR).**
   - Каналы R и B лежат в младших байтах двух 16-битных половин слова (`RB = 0x00FF00FF`). `div255_pair` делит обе половины сразу. Каждая половина `y ≤ 65152`, поэтому `y + 1 + (y >> 8) ≤ 65407` не переносится в соседнюю.
   - `blend`: R и B парой, G отдельно — 4 умножения вместо 6.
   - `over`: пары (R, B) и (A, G); альфа слоя — канал со значением 255, потому что `mul(255, α) = α`. 4 умножения вместо 7.
   - `composite`: R и B парой, G отдельно — 2 умножения вместо 3. Канал не переполняется, потому что `t_c ≤ t_a`.
   - Формулы ADR-0002 / ADR-0013 / ADR-0014 те же. Равенство прежним поканальным формулам проверено перебором всех входов канала и 2²⁰ пикселями с разными каналами (`tests/soft_pixel_math.rs`). Шейдер не меняется.

## Альтернативы и обоснование

| Вариант | Почему не выбран |
|---|---|
| Флаг в API «наложение то же, что в прошлом кадре» (О1 — б) | меняет API и переносит ошибку на клиента; сравнение 4 800 ячеек стоит микросекунды |
| Не перерисовывать строки под неизменным наложением | меняет правило ADR-0014 и полосы `damage`; не ускоряет кадр, где основной экран меняется, — отдельная задача |
| `opt-level = 3` | меняет профиль §10.2 и размер бинарника — решение владельца, вне задачи |
| Многопоточная отрисовка по полосам | архитектурное изменение (потоки, NFR-6) несоразмерно задаче |

## Последствия

- **Плюсы:**
  - `--bench --backend=soft --overlay` (наложение неподвижно): 23,7 → 48,2 FPS после кэша, **65,4–70,7 FPS** после пар каналов — NFR-5 выполнено.
  - Без наложения — 103,6–114,9 FPS (до задачи 103,1).
  - Кадр бит в бит прежний: golden и GL ↔ Software (8 сцен, оба уровня) без изменений.
- **Минусы / риски:**
  - Наложение, которое меняется каждый кадр (анимация), кэш не ускоряет — только пары каналов. Худший случай не замерялся.
  - Копия записей — ещё 16 Б на ячейку записи.
  - Ошибка условия инвалидации кэша оставит на экране устаревшую текстуру. Защита — тесты `tests/overlay.rs` (меняющийся экран, смена ячейки, исчезновение и возврат, размер окна, смена сетки, смена DPI при том же размере сетки в пикселях).
