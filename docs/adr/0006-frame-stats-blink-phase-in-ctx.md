# ADR-0006. Статистика кадра и фаза мигания в `Ctx`, уведомление `on_frame`

- **Дата:** 2026-10-02
- **Статус:** Accepted (частично заменён 0012: мигание, `INVERSE` и таймер удалены)
- **Тема:** расширение API событий (ADR-0004) данными, нужными демо для FR-27 (счётчик FPS, курсор в противофазе с `BLINK`) и для замеров NFR-4/NFR-5 (`--bench`); ТЗ FR-7, FR-27, NFR-4, NFR-5, §5.2, §13

## Контекст

1. FR-27 требует счётчик FPS в строке статуса демо. Кадры рисует `App` внутри `RedrawRequested`; приложение не видит ни их числа, ни длительности — считать FPS ему нечем.
2. NFR-4 («200×60 на GL ≤ 1 мс CPU на кадр: сборка данных + `glTexSubImage2D`») и NFR-5 («120×40 Software ≥ 60 FPS при полной перерисовке») никогда не замерялись. Владелец выбрал замер флагом демо `--bench`. Для него приложению нужно (а) гнать кадры непрерывно — сейчас перерисовка идёт только по запросу из обработчика события или по тику мигания; (б) знать длительность каждого кадра, причём для GL — **без** ожидания VSync: `GlBackend::render` = `render_into` (CPU-часть) + `swap_buffers` (блокируется до кадра монитора при `SwapInterval::Wait(1)`).
3. Владелец постановил: курсор демо мигает **в противофазе** с символами `BLINK`. Сейчас демо переключает видимость курсора на каждый `on_tick`, стартуя с «видим», — то есть **синфазно** с `BLINK` (`Blinker::new` стартует с видимой фазы). Хуже того, после `Blinker::catch_up` при пропуске нескольких переключений за одно пробуждение чётность «своего» счётчика у приложения расходится с фазой библиотеки. ADR-0004 уже назвал этот риск: «у приложения нет отдельного способа узнать фазу мигания изнутри `Ctx`».

## Решение

1. **`Ctx` расширяется двумя полями:** `blink_phase: bool` — фаза, с которой библиотека отрисует следующий кадр (`true` — `BLINK` виден), и `stats: FrameStats` — копия статистики кадров на момент события. Оба — значения, не ссылки: приложение их читает, библиотека остаётся единственным владельцем состояния.
2. **`FrameStats { frames: u64, cpu: Duration, total: Duration }`** считается в `App::render_frame`: `total` — весь кадр, включая `swap_buffers` (GL) или копирование в поверхность и `present` (Software); `cpu` — для GL длительность `render_into` (сборка данных, загрузка текстур, draw call — ровно то, что меряет NFR-4), для Software — длительность `render` без копирования в окно. GL-бэкенд запоминает длительность `render_into` в поле и отдаёт её методом `last_cpu_time()`; трейт `Renderer` не меняется. Стоимость — два-три `Instant::now()` на кадр, без аллокаций (NFR-6).
   **Уточнение по первому замеру (2026-10-02):** при включённом VSync драйвер (NVIDIA 581, Windows) возвращает из `swap_buffers` сразу, а ждёт кадра монитора в **первом GL-вызове следующего кадра** — `cpu` оказался 16,1 мс на 60 Гц, то есть равен периоду монитора и ничего не говорит о NFR-4. Поэтому добавлена опция `AppOptions::vsync` (по умолчанию `true`) → `GlOptions::vsync` → `SwapInterval::DontWait`; `--bench` выключает VSync, и тогда `cpu` — настоящая CPU-часть, а `total` — честный максимум FPS без ограничения монитором.
3. **Новый метод трейта `AppHandler::on_frame(&mut self, ctx: &mut Ctx<'_>)`** с пустым телом по умолчанию — вызывается после каждого **успешного** кадра (после повтора или отката кадр считается, когда он наконец отрисован). Это единственный способ для приложения запросить следующий кадр сразу после предыдущего — так работает `--bench`. Безусловный `ctx.redraw()` из `on_frame` даёт непрерывную перерисовку — это документируется как свойство, а не запрещается: именно оно нужно замеру.
4. **Демо** обновляет строку статуса (FPS, `cpu`) по `on_tick`, а не по `on_frame`: запись в экран из `on_frame` породила бы бесконечную перерисовку; тик мигания — естественный такт 2 Гц. При `--no-blink` счётчик не обновляется — это режим замера простоя, где FPS бессмысленен. Курсор демо рисуется при `!ctx.blink_phase`.

## Альтернативы и обоснование

| Вариант | Почему отклонён |
|---|---|
| Передавать фазу параметром `on_tick(phase, ctx)` | ломает сигнатуру существующего метода у интеграторов; фаза нужна и в других обработчиках (клавиша нажата — курсор перерисовать в текущей фазе), а не только на тике |
| Приложение считает фазу само по счётчику тиков | расходится с библиотекой после `catch_up` (пропущенные переключения); дублирует состояние, у которого уже есть единственный источник — `Blinker` |
| Статистика через отдельный метод `App::stats()` | `App` недоступен приложению внутри обработчиков (цикл владеет им); пришлось бы вводить `Rc<RefCell<_>>` или глобальное состояние |
| Замер `--bench` без окна, прямым вызовом рендереров (как `tests/stage4_gl`) | для GL нужен контекст — всё равно окно; `render` без `swap_buffers` для GL не вызвать снаружи, а `render_to_frame` добавляет `glReadPixels`; владелец выбрал флаг демо, и замер в настоящем окне ближе к условиям NFR-4 («60 FPS на интегрированной графике») |
| Мерить `cpu` при включённом VSync (первоначальный план) | опровергнуто замером: ожидание кадра монитора ложится в первый GL-вызов следующего кадра, и `cpu` равен периоду монитора. Поэтому `--bench` выключает VSync (`AppOptions::vsync = false`), а в обычном режиме VSync остаётся |
| `glFinish` после `swap_buffers`, чтобы ожидание не переезжало в следующий кадр | меняет горячий путь обычного режима ради измерения и убивает перекрытие CPU/GPU; выключение VSync локально для замера |
| Передавать `cpu` через расширение трейта `Renderer` (`fn last_cpu_time`) | Software-рендереру нечего разделять (у него нет swap); метод на `GlBackend` локальнее и не меняет публичный трейт |

## Последствия

**Плюсы:** демо и любое приложение получают FPS и время кадра без собственных часов; курсор приложения синхронизируется с фазой библиотеки точно, а не «по счётчику»; `--bench` воспроизводим одной командой; `Renderer` и существующие шесть методов `AppHandler` не меняются — интеграторы ничего не правят.

**Минусы / риски:** `Ctx` стал шире — поля копируются при каждом событии (две `Duration`, `u64`, `bool` — пренебрежимо); `on_frame` даёт приложению возможность случайно устроить петлю перерисовки — свойство описано в документации трейта; `cpu` на GL не включает фактическое выполнение на GPU (draw call асинхронен) — это соответствует формулировке NFR-4, но FPS GL в `--bench` упирается в частоту монитора, и это нужно читать правильно.
