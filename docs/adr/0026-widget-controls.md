# ADR-0026. Контролы `gterm-widgets`: описание экрана `ui()`, трейт `Control` на состоянии, сообщения приложения как в iced, модальный слой на `Popup`

- **Дата:** 2026-10-30
- **Статус:** Accepted (ТЗ `docs/spec/2026-10-30-widget-controls.md` утверждено владельцем 2026-10-30; решения О1–О5 — §6 ТЗ). Отменяет направление черновика `2026-10-27-widget-focus` (отклонён владельцем 2026-10-30, перезапуск с чистого листа).
- **Тема:** ТЗ §13; ADR-0004, ADR-0014, ADR-0023. План — `docs/plans/2026-10-30-widget-controls.md`, исследование — `docs/research/2026-10-30-controls-interview.md`.

## Контекст

Виджеты части 1 (ADR-0023) не обрабатывают ввод: фокус и клавиши приложение разводит вручную (`examples/widgets.rs` — `enum Focus` и `match`). Владелец строит на `gterm` приложение класса «панели и диалоги» (файл-менеджер) и хочет описывать экран один раз, получая от крейта раскладку, отрисовку, обход фокуса, доставку клавиш и мыши и смысловые события; свои контролы (панель файлов) должны быть равноправны встроенным. `gterm` отдаёт мышь в физических пикселях и не сообщает модификаторы и размер ячейки (`app/api.rs`, `app/events.rs`).

## Решение

1. **Контрол — трейт `Control<M>` на состоянии**, не на виджете: общий блок `NodeState { focused, area, captured }` через `node()/node_mut()`, `focusable()`, обработчики `key`/`mouse` с ответом `Handled::{Yes, No}`. Встроенные состояния (`ListState`, `TableState`, новый `ButtonState`) и типы приложения реализуют его одинаково; паттерн «состояние у приложения, виджет-значение задаёт вид» (ADR-0023) сохраняется: свой контрол рисует себя сам (`Drawable`), встроенный — виджетом через `Ui::stateful`, а о своих событиях (выделение изменилось, активирован) сообщает дереву через `WidgetEvents`, не зная типа сообщений приложения. Флаги фокуса и области живут в состоянии: идентификаторов, арены и долгоживущего дерева нет; `ListState`/`TableState` теряют `Copy` (карта видимых строк для клика).
2. **Описание экрана `Ui<'a, M>`** — временная структура из `&mut` на состояния приложения, строится функцией `ui()` на каждое событие и кадр; контейнеры (`split`, `group` с рамкой) прозрачны для фокуса; одно описание служит раскладке, отрисовке, обходу фокуса и попаданию мыши. `Box<dyn …>` только в этом временном векторе.
3. **Сообщения как в iced**: механизм параметризован типом сообщения приложения `M`; встроенные контролы получают привязки при описании (`on_select`, `on_activate`, `on_escape`), свой контрол публикует сам через `&mut Messages<M>` аргументом обработчика; результат маршрутизации — «обработано/нет» плюс собранные сообщения, адрес контрола не передаётся; приложение разбирает сообщения после сброса описания и затем перерисовывает.
4. **Фокус и ввод**: `Tab`/`Shift+Tab` по кольцу листьев в порядке объявления в глубину; клавиши — контролу под фокусом, иначе приложению (глобальные клавиши — на необработанном); мышь в ячейках — верхнему контролу под указателем, левый клик даёт фокус до доставки, захват от принятого нажатия до отпускания любой кнопки или ухода указателя (кнопка захвата не хранится — одна кнопка за раз); кнопка активируется отпусканием внутри области. Ячейка под указателем считается библиотекой с учётом центрирования сетки в окне (`app::pointer_cell`, §7.2 `u_origin`).
5. **Модальный слой** — часть того же описания (`.modal(...)`): весь ввод ему; мышь слой поглощает целиком — и вне области, и внутри мимо контролов (экрану под ним ничего не достаётся); `Esc` → привязка `on_escape` или «не обработано»; `focus_*` описания относятся к основному экрану, фокус внутри слоя двигает только ввод слою; рисуется через `Popup`, который остаётся с прежним API в `widgets/popup.rs`.
6. **`gterm` расширяется добавлением**, типы `winit` остаются (ADR-0004): `PointerEvent::{Moved, Input, Wheel}.cell` — ячейка под указателем, `Ctx::modifiers` (обработка `ModifiersChanged`), `Ctx::cell_px`.

## Альтернативы и обоснование

| Вариант | Почему отклонён |
|---|---|
| Контролы-объекты, приложение само разводит фокус и события коротким явным кодом | ручной код на каждый экран и каждый контрол — главный риск pre-mortem владельца |
| Долгоживущее дерево объектов с владением детьми (Turbo Vision) | динамическая диспетчеризация и доступ к данным через дерево; расходится с временным `ui()` и состояниями у приложения |
| Адрес контрола (путь индексов, идентификатор) в результате маршрутизации | не нужен при сообщениях приложения; оставлен как задел на будущее |
| Перевод пикселей в ячейки только в крейте виджетов | приложения без виджетов считали бы сами; ячейка в событии дешевле и не ломает ADR-0004 |
| Пересмотр контракта ввода `gterm` целиком (свои типы событий) | отмена ADR-0004, правка всех приложений и оконных тестов |
| Фокусируемые контейнеры, два уровня Tab/стрелки | лишняя сложность; контейнеры прозрачны, свой контрол — одна единица фокуса |
| Упразднение `Popup` в пользу слоя | ломает API части 1; слой использует `Popup` внутри |
| Активация кнопки по нажатию без захвата | непривычно; владелец выбрал отпускание внутри, захват вошёл в объём |

## Последствия

**Плюсы:** экран описывается один раз; свои контролы — один тип приложения с полем `node` и реализацией трейта; сообщения типизированы приложением, разбор в одном месте; `Popup` и виджеты части 1 не меняются; `gterm` меняется добавлением полей.

**Минусы / риски:** описание держит `&mut` на все состояния, пока живёт — порядок «маршрутизация → разбор → отрисовка» обязателен; обобщение по `M` проходит через весь модуль `ui`; `Vec` и `Box` на узел в обработчиках событий (не в кадре рендерера — NFR-6 не затронут); карта строк и области в состояниях соответствуют последнему кадру; `ModifiersChanged` на окне не проверяется автоматически. Размеры release — в `docs/done/2026-10-30-widget-controls.md` после реализации.
