# ADR-0016. Software: отрисовка полосами строк в пуле потоков `rayon`

- **Дата:** 2026-10-10
- **Статус:** Accepted
- **Тема:** §8, NFR-5, NFR-6, NFR-7, NFR-9, NFR-1. ТЗ задачи — `docs/spec/2026-10-10-soft-threads.md`, план — `docs/plans/2026-10-10-soft-threads.md`.

## Контекст

Software-рендерер рисовал кадр в одном потоке: 7,9 мс без наложения и 13,2 мс с наложением на весь экран (120×40, release). Прототип с `thread::scope` показал почти линейный рост до 4 потоков (231 FPS с наложением против 71).

Ограничения проекта:
- **NFR-6** — нет выделений памяти в кадре. `thread::scope` создаёт потоки каждый кадр, это 13 выделений на кадр (замер счётчиком).
- **NFR-9** — `unsafe` только в `gl_backend.rs`. Свой постоянный пул на `std` не может принимать одолженные на время кадра данные (`&mut` полосы кадра, `&Atlas`, `&ScreenBuffer`) без стирания времени жизни, то есть без `unsafe`.

Решения владельца (2026-10-10): О1 — `rayon`; О2 — не больше 4 потоков; О3 — делать сейчас.

## Решение

1. **Пул.**
   - `SoftBackend` владеет `rayon::ThreadPool` (`Option`). Потоки создаются в конструкторе, их `min(available_parallelism, 4)`.
   - `SoftBackend::with_threads(atlas, n)` — для тестов и замеров; `threads()` — сколько потоков на деле.
   - Пул не создался — рисуем в текущем потоке, причина в stderr (NFR-7).
2. **Полосы.**
   - Кадр (с начала сетки) и текстура наложения режутся `par_chunks_mut` на непрерывные полосы строк сетки, по полосе на поток. Полосы не пересекаются, всё остальное (атлас, экран, отметки строк, текстура при отрисовке кадра) только читается, поэтому `unsafe` не нужен.
   - Замер: `par_chunks_mut` в постоянном пуле — 0 выделений за 20 кадров.
3. **Одна реализация.**
   - Отрисовка полосы — `MainPass::draw_band` (основной слой и наложение текстуры на свои строки) и `OverlayPass::build_band` (сборка текстуры) в `src/renderer/soft_band.rs`.
   - Однопоточный путь вызывает ту же функцию на весь кадр. Прежние методы `draw_row`/`draw_cell`/`fill_pixel`/`composite_row`/`draw_overlay_cell` перешли в эти функции.
4. **Порядок кадра.** Подготовка глифов (меняет атлас) — в текущем потоке. Затем текстура собирается до основного слоя: она от кадра не зависит. Затем один параллельный проход: строки основного слоя и наложение на них.
5. **Порог.** Если строк к отрисовке меньше `PARALLEL_MIN_ROWS = 8`, всё рисуется в текущем потоке. Ввод с клавиатуры обычно меняет одну строку, и раздача полос стоила бы дороже работы.

## Альтернативы и обоснование

| Вариант | Почему не выбран |
|---|---|
| `std::thread::scope` на каждый кадр | 13 выделений на кадр — нарушает NFR-6 |
| Свой постоянный пул на `std` | одолженные данные кадра в постоянные потоки — только через `unsafe` (NFR-9) |
| Свой пул с `Arc`/`Mutex` и владением данными | кадр пришлось бы хранить отдельными полосами, вывод в окно и `frame()` переделывать; несоразмерно |
| Больше 4 потоков | 6 → 12 потоков дают +12 % при вдвое большем числе потоков; Software часто работает на ВМ и RDP с 2–4 vCPU |

## Последствия

- **Плюсы** (release, 120×40):
  - без наложения 111 → **331–340 FPS**, `cpu` 7,9 → 1,9 мс;
  - с наложением 70 → **244–253 FPS**, `cpu` 13,2 → 2,9 мс;
  - один поток тоже быстрее прежнего (6,7 / 10,1 мс): отрисовка полосы режет строку кадра срезом без проверки границ на каждый пиксель;
  - кадр с одной изменённой строкой 160 → 138–142 мкс;
  - кадр не зависит от числа потоков (тест на 1 и 4 потоках, golden, GL ↔ Software).
- **Минусы / риски:**
  - Новая зависимость `rayon` 1.12 (`rayon-core`, `crossbeam-*`, `either`); `demo.exe` +28 160 Б (1 482 240 Б).
  - Каждый `SoftBackend` держит до 4 спящих потоков. Нагрузку на CPU в простое нужно проверить на машине владельца.
  - Подготовка глифов и вывод в окно остаются однопоточными: после 4–6 потоков упираемся в них.
