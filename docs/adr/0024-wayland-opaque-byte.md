# ADR-0024. Буфер окна Wayland получает непрозрачный старший байт `0xFF`

- **Дата:** 2026-10-25
- **Статус:** Accepted (решение владельца 2026-10-25: только Wayland, при копировании кадра в буфер окна; зонд удалён).
- **Тема:** ТЗ §7.3, §11.3, NFR-7; ADR-0010 (вывод Software в окно), ADR-0013 (формат пикселя кадра). Отчёт — `docs/done/2026-10-25-wayland-opaque-byte.md`.

## Контекст

На Linux KDE Plasma (KWin 6.8, Wayland, дробный масштаб 1.7) Software-бэкенд показывал окно «полупрозрачным»: сквозь него просвечивал фон, кадры при перерисовке складывались друг с другом, и картинка белела. GL и GLES на том же компоновщике и тот же Software на X11 с тем же масштабом (`WINIT_X11_SCALE_FACTOR=1.7`) — чисто.

Диагностика (`--debug`, пробные тесты, зонд):

1. Путь показа и кадр `gterm` исключены: все показы — ветка «full copy» с совпадающими размерами; частичная перерисовка Software при ячейке 22×49 совпадает с кадром с нуля (0 отличающихся пикселей); пиксель кадра пишется присваиванием, предыдущий кадр в формулу не входит.
2. Гипотеза о повреждении (`damage_buffer` точным прямоугольником вместо `i32::MAX`, как у Mesa) проверена и отвергнута: артефакты те же.
3. Зонд `winit` + `softbuffer` без единой строки `gterm` (коммит `d17a8a2`, рамка, синяя половина, бегущая шахматная доска) показал те же артефакты. С записью `0xFF` в старший байт каждого пикселя картинка стала чистой и устойчивой при движении мыши и перемещении окна.

Кадр Software — `0x00RRGGBB` (`encode_color`, ADR-0013), `softbuffer` 0.4.8 создаёт буферы `wl_shm` формата `Xrgb8888`, где старший байт по протоколу игнорируется. KWin 6.8 при дробном масштабе читает его как предумноженную альфу: альфа 0 при ненулевом цвете — чистое сложение с фоном и с предыдущим содержимым, отсюда «прозрачность», накопление и белый цвет.

## Решение

1. **Только Wayland, только при копировании в буфер окна.** `SoftState` узнаёт платформу при создании по сырому дескриптору окна (`RawWindowHandle::Wayland`, `chain.rs::software_on`); `present` копирует кадр через `copy_to_window`: на Wayland — `pixel::copy_opaque` (`pixel | 0xFF00_0000` на пиксель), на X11 и Win32 — прямая `copy_from_slice`. Оба пути показа — полный и полосами — идут через одну функцию.
2. **Формат кадра не меняется.** `encode_color` остаётся `0x00RRGGBB`: golden-эталоны, тесты пиксельной арифметики, сравнение GL ↔ Software и наложение не затронуты.
3. `copy_opaque` проверяет равенство длин срезов (Fail Fast) и покрыта тестом в `tests/soft_pixel_math.rs`: цвет без изменений, старший байт `0xFF` у каждого пикселя, паника при разных длинах.

## Альтернативы и обоснование

| Вариант | Почему отклонён |
|---|---|
| `0xFF` на всех платформах при копировании | лишнее OR на пиксель на X11 и Win32, где байт игнорируется (`put_image`, `BitBlt`); проверка платформы — одно `bool` |
| `0xFF` в самом кадре (`encode_color` → `0xFFRRGGBB`) | меняет формат кадра: перезапись golden, правка пиксельной арифметики и масок сравнения с GL; самый широкий дифф ради одного компоновщика |
| Повреждение `i32::MAX` вместо точного прямоугольника | проверено на машине владельца — не помогает (гипотеза отвергнута, код снят) |
| Ждать исправления KWin или `softbuffer` | пользователи KDE видят мусор сейчас; обходной путь дёшев и локален |

## Последствия

**Плюсы:** Software на KWin Wayland чист; остальные платформы и формат кадра не затронуты; эталонный алгоритм §7.3 без изменений.

**Минусы / риски:** на Wayland полная копия кадра — OR на пиксель вместо `memcpy` (замер на Linux — за владельцем, `--bench --backend=soft`); `demo.exe` 1 542 656 Б (+2 048 Б). Причина на стороне KWin не локализована до строки — зонд даёт воспроизведение для сообщения об ошибке.
