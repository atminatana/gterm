# ADR-0033. Периодический тик приложения: период в `AppOptions` и `Request`, `AppHandler::on_tick`, ожидание до срока; без периода цикл спит как прежде

- **Дата:** 2026-11-13
- **Статус:** Accepted (частично заменяет 0012: п.3 «таймера в библиотеке нет» и отклонённую там альтернативу об общем тике; ТЗ `docs/spec/2026-11-13-tick-meter.md` утверждено владельцем 2026-11-13, О1–О3 — варианты (a))
- **Тема:** ТЗ FR-26, §5.3 п.4; ADR-0004, ADR-0006, ADR-0012. План — `docs/plans/2026-11-13-tick-meter.md`.

## Контекст

ADR-0012 убрал мигание ячеек вместе с таймером, `on_tick` и `WaitUntil`; общий тик для приложений был отклонён со словами «периодический таймер приложение заведёт само, если понадобится». На практике завести его приложение не может: свой поток с таймером нечем связать с циклом `winit` — пробуждения извне (`EventLoopProxy`) в библиотеке нет, а единственный обходной путь, запрос кадра из `on_frame`, гонит кадры непрерывно. Потребность появилась у приложения с индикаторами уровня и таймерами на экране (`sf2_player`): ему нужен вызов около 30 раз в секунду без пользовательского ввода и без перерисовки в простое. Владелец решил (2026-11-13) вернуть общий тик в библиотеку.

## Решение

1. **Период.** `AppOptions::tick_period: Option<Duration>` — начальное значение, по умолчанию `None`. `Request::tick_period: Option<Option<Duration>>` — смена на лету из любого обработчика: `Some(Some(period))` задаёт, `Some(None)` выключает. Период короче 1 мс считается за 1 мс.
2. **Обработчик.** `AppHandler::on_tick(&mut self, ctx: &mut Ctx<'_>)` с пустым телом по умолчанию; вызывается на главном потоке тем же путём, что остальные обработчики (`notify` → `apply_request`).
3. **Цикл.** Срок проверяется в `ApplicationHandler::about_to_wait` — перед каждым ожиданием, а не по причине пробуждения: тик приходит и тогда, когда цикл занят вводом или кадрами. Срок наступил — один вызов `on_tick`. Затем режим ожидания: `ControlFlow::WaitUntil(срок)` при заданном периоде, `ControlFlow::Wait` без него.
4. **Отставание не догоняется.** Следующий срок — «момент возврата из обработчика плюс период»: после задержки приходит один тик, а не серия. Смена периода начинает отсчёт заново с момента применения запроса.
5. **Тик не запрашивает кадр.** Перерисовка — только по `ctx.redraw()` из обработчика.
6. До создания окна и после запроса выхода тики не приходят. Состояние (период, срок) — `app/tick.rs`.
7. **Что не возвращается из убранного ADR-0012:** мигание ячеек, флаг `BLINK`, фаза в `Ctx` и шейдере, частичная перерисовка мигающих строк. Таймеров у виджетов по-прежнему нет: `Control::tick`/`Ui::tick` ведёт приложение (из `on_frame` или из `on_tick`).

## Альтернативы и обоснование

| Вариант | Почему не выбран |
|---|---|
| Библиотека даёт только пробуждение извне (`EventLoopProxy` + `on_wake`), таймерный поток заводит приложение | межпоточный механизм, которого в библиотеке нет вовсе; приложению — лишний поток и его остановка; для задачи «звать раз в N мс» избыточно. Таймерный поток уже отклонялся в ADR-0032 как второй источник событий мимо цикла |
| Без правки библиотеки: непрерывные кадры из `on_frame` | окно перерисовывается постоянно даже при неизменном экране — расход CPU и GPU в простое |
| Период только в `Request` (О1 b) | приложению пришлось бы включать тик из первого пришедшего обработчика; параметр цикла естественнее задать при запуске |
| Держать сетку времени: срок от назначенного времени предыдущего тика (О2 b) | после задержки дал бы тики подряд или неравномерные интервалы; индикаторам нужен свежий вызов, а не серия |
| Каждый тик запрашивает кадр (О3 b) | перерисовка при неизменном экране; решать, изменилось ли что-то, должно приложение |
| Проверять срок по причине пробуждения (`new_events` + `StartCause::ResumeTimeReached`) | при непрерывном вводе или кадрах цикл не засыпает, срок не «достигается», и тик не пришёл бы |

## Последствия

- **Плюсы:** приложение получает периодический вызов без своих потоков и без перерисовки в простое; без заданного периода поведение прежнее — цикл в `Wait`, `on_tick` не вызывается, существующие приложения и тесты не затронуты; всё в одном потоке.
- **Минусы / риски:** FR-26 («в простое приложение не потребляет CPU») теперь выполняется только для приложений без периода — ТЗ приведено к этому в версии 1.28. `AppOptions` и `Request` получили по одному публичному полю: внешний код, создающий `AppOptions` литералом без `..Default::default()`, перестанет собираться. Точность — как у системного таймера (`WaitUntil` на Windows — до ~15 мс); гарантируется только «не раньше срока». На Linux и Wayland поведение автоматически не проверялось (хост разработки — Windows).
- **Проверка:** оконный тест-бинарник `tests/tick_events.rs` (`harness = false`, четыре сценария дочерними процессами): период из `AppOptions` и кадр только по запросу, отсутствие тиков без периода, смена и выключение через `Request`, отставание без догонки.
