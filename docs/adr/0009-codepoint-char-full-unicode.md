# ADR-0009. Кодовая точка — `char` во всём диапазоне Unicode; плоская таблица «кодовая точка → слот»

- **Дата:** 2026-10-08
- **Статус:** Accepted. Уточняет ADR-0001 п.6 и ADR-0003 в части «область — кодовые точки BMP».
- **Тема:** `Cell::ch`, ключ атласа, API буфера/атласа/растеризатора (ТЗ FR-2, FR-4, FR-8.4, FR-9, §6.1, §13); план — `docs/plans/2026-10-08-codepoint-u32.md`

## Контекст

`Cell::ch: u16` и таблица атласа на 65 536 записей ограничивают отображение плоскостью BMP. Решение принималось под PT Mono (ADR-0001), у которого все глифы в BMP. У нынешнего RobotoMono Nerd Font Mono по разбору `cmap` 6 896 глифов вне BMP (Material Design Icons, U+F0001–U+F1AF0) — они недоступны. Будущие SVG-глифы (ADR-0008) нуждаются в свободном диапазоне без конфликтов с иконками шрифта; такой есть только вне BMP (плоскость U+100000–U+10FFFD). Кроме того, `ScreenBuffer::write_str` приводит `char` к `u16` и молча обрезает символы вне BMP (U+F0001 → U+0001).

Рендереры передают на GPU **номер слота**, а не кодовую точку (§6.1), поэтому ширина кодовой точки не затрагивает шейдер, текстуру данных и страницу атласа.

## Решение

1. **Тип кодовой точки — `char`** во всём публичном API: `Cell::ch`, `ScreenBuffer::set_cell`/`fill_rect`, `Atlas::ensure`/`slot_of`/`glyph`, `Rasterizer::has_glyph`/`rasterize`, `box_drawing`. Пустая ячейка — `'\0'`. `write_str` пишет `char` как есть.
2. **Таблица «кодовая точка → слот» — плоский массив** `Vec<u16>` на `0x110000` записей (2,2 МБ), индекс — `ch as usize`, доступ O(1) как прежде. Сброс страницы заливает весь массив. `codepoint_of_slot` хранит `char`.
3. **Слот остаётся `u16`;** раскладка данных GPU (§6.1: `R = slot | flags << 16`) не меняется.
4. **`Cell::to_packed`/`from_packed` сохраняются** с новой раскладкой: `[0] R = ch` (32 бита), `[1] G = fg`, `[2] B = bg`, `[3] A = flags`. Эта упаковка не совпадает с данными GPU, где в R лежит слот; так было и раньше.
5. Перебор «всех глифов шрифта» (бинарник `full_table`) идёт по `cmap` шрифта, а не по диапазону кодовых точек.

## Альтернативы и обоснование

| Вариант | Почему не выбран |
|---|---|
| `u32` вместо `char` | допускает значения > U+10FFFF и суррогаты — нужна проверка в атласе; литералы требуют приведений. `char` даёт те же 4 байта с гарантией допустимости от компилятора |
| Двухуровневая таблица по плоскостям (17 × 64 К, по требованию) | экономит память (128 КБ на занятую плоскость), но больше кода и одно обращение к памяти лишнее; 2,2 МБ рядом со страницей 16 МБ несущественны |
| `HashMap` | хэширование на каждую ячейку каждого кадра (`slot_of` в горячем пути GL) |
| Удалить `to_packed`/`from_packed` (в рендерерах не используются) | меняет публичный API сверх задачи; канал A и так был резервом |
| Ключ «кодовая точка + шрифт», LRU, вторая страница (§13 целиком) | несколько шрифтов не требуются; страница вмещает экран, `full_table` листает постранично со сбросом |

## Последствия

- **Плюсы:** доступны все глифы шрифта, включая иконки вне BMP; исчезает молчаливая обрезка в `write_str`; у SVG-глифов появляется свободная плоскость; шейдер, данные GPU и golden-эталоны не меняются.
- **Минусы / риски:**
  - Ломающее изменение публичного API (внешних потребителей пока нет).
  - `Cell` растёт с 12 до 16 байт.
  - Таблица атласа — 2,2 МБ вместо 128 КБ, сброс страницы заливает её целиком (редко: переполнение, смена DPI).
  - Все глифы шрифта (~11,9 тыс.) не помещаются на одну страницу при крупной ячейке — `full_table` опирается на сброс атласа при листании.
