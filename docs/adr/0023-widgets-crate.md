# ADR-0023. Набор виджетов `gterm-widgets`: отдельный крейт, немедленный режим по образцу ratatui, `ScreenBuffer` как буфер

- **Дата:** 2026-10-23
- **Статус:** Accepted (решения владельца 2026-10-23: О1 — рисовать прямо в `ScreenBuffer`, О2 — жадная раскладка, О3 — часть 1: `Block`, `Paragraph`, `List`, `Table`, `Popup`, О4 — отдельный крейт).
- **Тема:** ТЗ §1, §13; ADR-0004, ADR-0013, ADR-0014, ADR-0017. ТЗ задачи — `docs/spec/2026-10-23-widgets.md`, план — `docs/plans/2026-10-23-widgets.md`, исследование — `docs/research/2026-10-23-ratatui-backend.md`.

## Контекст

Владелец выбрал свой набор виджетов для `gterm` вместо слоя совместимости с ratatui: `gterm` даёт то, чего в терминалах нет (альфа цветов, полупрозрачные наложения, процедурные рамки и мозаики), а слой совместимости не избавляет от правок в приложениях. Архитектура ratatui (немедленный режим, `Widget::render(self, area, buf)`, раскладка по ограничениям, `Span/Line/Text`) проверена практикой и знакома разработчикам — её берём как образец формы API, не копируя код (другой буфер, другая модель ячейки).

## Решение

1. **Отдельный крейт `crates/gterm-widgets`**, зависит только от `gterm` (и `bitflags` для `Borders`); `winit` — лишь для примера. Библиотека `gterm` не меняется; её размер и MSRV не затронуты; потребители подключают виджеты по желанию (фича в `gterm` включалась бы для всего графа и навсегда).
2. **Буфер — `ScreenBuffer`.** Виджеты пишут в него через расширение `BufferExt` с обрезкой по `Rect` и границам; второго буфера и диффа нет — dirty-строки и частичную перерисовку делает `gterm`.
3. **Форма API — как у ratatui:** `Widget`/`StatefulWidget`, `Rect` в `u16`, `Layout`/`Constraint`/`Direction`, `Style` с `patch`, `Span → Line → Text`, `ListState`/`TableState` у приложения. Совместимости типов нет и не обещается.
4. **Текст без графем:** одна кодовая точка — одна ячейка (модель `gterm`), ширина строки — число символов, перенос по словам, длинные слова — по символам.
5. **Раскладка жадная, без солвера:** `Length`/`Percentage`/`Min` задают стартовые длины (нехватка урезается с конца); остаток сначала получают `Max` до пределов поровну, затем `Fill` по весам, без `Fill` — `Min` поровну; остаток деления — первым элементам. Детерминирована, целочисленна, ≈150 строк.
6. **Рамки — процедурные** (`Plain`, `Rounded`, `Double`, `Thick`): стыкуются между блоками благодаря ADR-0002/0022. **`Popup`** — прямоугольник на сетке плюс прозрачный `ScreenBuffer` с фоном по альфе, рисуется `DrawCtx::draw_buffer` (ADR-0014).

## Альтернативы и обоснование

| Вариант | Почему отклонён |
|---|---|
| Слой совместимости с ratatui | требует правок в приложениях и моста потоков; не даёт альфы и наложений (исследование) |
| Фича `widgets` внутри `gterm` | размывает границу библиотеки отображения, включается для всего графа зависимостей, тяжёлые golden-тесты смешиваются с тестами виджетов, замеры NFR-1 нужно оговаривать |
| Свой буфер с диффом, как в ratatui | дифф и частичную перерисовку уже делает `gterm`; второй буфер — лишняя копия на кадр |
| Солвер ограничений (Cassowary) | зависимость или ≈1 000 строк ради случаев, которых у жадного алгоритма нет по построению |
| Копирование кода ratatui (MIT) | другой буфер и ячейка делают копирование бесполезным; заимствуется только форма API |

## Последствия

**Плюсы:** приложения на `gterm` получают знакомую модель UI без новых зависимостей; рамки, альфа и наложения — нативные; `gterm` и его тесты не затронуты.

**Минусы / риски:** нет графем и двухшириных символов; жадная раскладка отличается от ratatui на противоречивых ограничениях; состав части 1 ограничен пятью виджетами, остальное — второй задачей; размер release 2026-10-23: пример `widgets.exe` 1 186 816 Б, `demo.exe` 1 540 608 Б без изменений (`docs/done/2026-10-23-widgets.md`).
