# ADR-0005. Геометрия выводится из размера шрифта: целочисленного масштаба нет, DPI — множитель растеризации

- **Дата:** 2026-10-02
- **Статус:** Accepted
- **Тема:** размер ячейки, DPI, зум (ТЗ FR-8, FR-10, FR-13, FR-22, FR-23, FR-24, FR-28, §7.2, §7.3, §8)

## Контекст

ТЗ FR-13 требовало целочисленного масштабирования ячейки (`scale = 1, 2, 3…`), шейдер рисовал блок `scale × scale` на пиксель глифа, CPU-рендерер заливал такой блок через `slice::fill`. FR-24 требовала поддержки DPI, но описывала её как «подобрать `scale`». Пользовательский зум `+`/`-` (FR-28) менял этот `scale`.

Эта схема работает только при `scale_factor = 1`. На 200 %-мониторе ячейка в физических пикселях вдвое мельче, текст нечитаем, а единственный доступный «крупный текст» — целочисленный скачок `scale = 2`, при котором глиф растягивается в 2 раза: на 150 % это увеличение в 1,33 раза, на 125 % — в 1,6, то есть размер не пропорционален DPI, а «лесенка» на диагоналях неизбежна. Плюс FR-24 требовала увеличивать окно под фиксированную сетку, что плохо совмещается с тем, что размер окна задаётся числом ячеек.

Дополнительные соображения:

- Шрифт растеризуется один раз в атлас и живёт до сброса страницы (ADR-0003). Менять размер шрифта = пересобирать растеризатор (хинтеры строятся на конкретный размер) и сбрасывать страницу.
- Проверенная в проекте стоимость растеризации — ≈0,7 мс на глиф при 16 px; площадь растёт как размер².

## Решение

1. **Целочисленного масштаба нет.** `ViewParams.scale`, uniform `u_scale`, `fill_block` в CPU-рендерере и оптимизация «быстрый путь для `scale == 1`» удаляются. Один пиксель глифа = один пиксель кадра, `NEAREST` без интерполяции (FR-13).
2. **Единственный источник геометрии — метрики растеризации.** Размер ячейки равен `glyph_w × glyph_h`; из него выводятся сетка (`cols = w / glyph_w`), размер окна и всё остальное. Рендереры не содержат ни констант, ни коэффициентов размера (FR-10).
3. **Формула физического размера:** `glyph_px = clamp(round(FONT_SIZE_PX · FONT_SCALE · scale_factor), 8, 48)`.
   - `FONT_SIZE_PX = 16` — **логический** размер шрифта (физический при `scale_factor = 1`);
   - `FONT_SCALE` — множитель пользователя, в 1.0 константа `1.0`; точка подключения будущего файла настроек (сегодня требования к файлу настроек в ТЗ нет, FR-19 описывает только CLI и `TERM_BACKEND`);
   - `scale_factor` берётся у созданного окна (`Window::scale_factor()`), при смене — из `ScaleFactorChanged`, предложенный системой размер окна принимается через `InnerSizeWriter` (иначе окно прыгает при переносе между мониторами);
   - не-конечные, нулевые и отрицательные значения трактуются как `1.0` (`f64::clamp` с `NaN` даёт `NaN`, округление упало бы в ноль и привело к панике в растеризаторе).
4. **Границы размера.** Нижняя 8 px: меньше ячейка нечитаема, метрики дают ячейку ≈5 px. Верхняя 48 px: при странице 1024 (минимум `GL_MAX_TEXTURE_SIZE`) глиф 48 px даёт 21×21 = 441 слот, а 64 px — лишь 16×16 = 256, чего не хватает даже для постраничной таблицы глифов шрифта (FR-27) и приводит к ошибке «страница не вмещает» с откатом на Software. Значение закрепляется тестом: ёмкость при 48 px на странице 1024 — не меньше 400.
5. **Начальный размер окна — в логических единицах** (`LogicalSize`), иначе на 200 %-мониторе окно вдвое меньше задуманного, а потом «прыгает», когда определится DPI.
6. **Пользовательского зума нет.** `+`/`-` исключены из FR-28; API не содержит методов изменения размера. `FONT_SCALE` — константа.
7. **Пересборка атласа при смене размера.** `Rasterizer` строится на конкретный размер; смена `glyph_px` пересобирает хинтеры и переносит растеризатор в новый атлас. Страница атласа переиспользуется (16 МБ не перевыделяются), слоты инвалидируются через уже существующий счётчик сбросов, глифы растеризуются лениво по мере показа.
8. **Бюджет растеризации на кадр не вводится.** Одна пауза на 0,25–0,9 с возникает при переносе окна между мониторами с разным DPI (при старте её не видно — окно скрыто до первого кадра, FR-22). Рывок принят сознательно: при отсутствии зума событие редкое, а бюджет требовал бы гарантии завершения (иначе риск вечного цикла перерисовки в противоречие FR-26).
9. **Режимы сетки не трогают размер шрифта.** `AutoGrid` (по умолчанию) пересчитывает `cols/rows` по окну; `FixedGrid` держит сетку, а не помещающуюся в окно часть центрирует и обрезает по границе окна.

## Альтернативы и обоснование

| Вариант | Почему отклонён |
|---|---|
| Оставить целочисленный `scale`, а DPI умножать на него (`user_scale · round(dpi)`) — вариант из плана этапа 6 | 150 % → `scale = 2`, то есть увеличение в 1,33 раза вместо 1,5; на 125 % — в 1,6; размер не соответствует DPI, диагонали получают «лесенку» |
| Игнорировать DPI (текущее поведение) | на 200 % текст вдвое мельче системного, окно в половину меньше нужного |
| Пересчитывать размер шрифта под DPI, но оставить целочисленный `scale` для зума | две независимые величины, отвечающие за одно (размер текста): зум «×2» поверх 24 px даёт то же, что `+2 px`, но с растяжением растра |
| Ограничить `glyph_px` сверху 255 (как `cell_metrics`) | при 255 px страница 1024 вмещает 4×4 глифа: переполнение на каждом втором экране, лишний откат GL → Software |
| Разрешить дробный размер ячейки (например, 23,5 px) | метрики целочисственные, дробный остаток всё равно округляется один раз; целочисленный размер ячейки нужен и атласу, и раскладке |
| Пропорциональное (нецелочисленное) увеличение растра в шейдере | запрещено FR-13 (`NEAREST`, без интерполяции) и разрушило бы бит-идентичность GL и Software |
| Бюджет растеризации на кадр | см. п.8 |

## Последствия

**Плюсы:** текст на любом DPI ровно пропорционален системному и без растяжения; геометрия выводится из одного места, в рендерерах нет ни констант, ни коэффициентов (проще шейдер: деление на `u_scale` исчезло); зум не нужен и не стоит перерастеризации; `FontFamily::metrics_at(size)` и `Atlas::set_rasterizer` — единственные новые точки, через которые проходит размер.

**Минусы / риски:** смена размера шрифта дорога (пересборка хинтеров + сброс страницы + выгрузка 16 МБ в GL) — приемлемо, потому что единственный триггер в 1.0 это смена DPI монитора, и пауза происходит под скрытым окном при старте; при `scale_factor > 3` шрифт упирается в 48 px (сознательно, «эффективный DPI» ограничен 3.0); golden-эталон для «увеличенной» сцены перегенерируется — это новая картинка (другой хинтинг на 32 px), а не растянутая старая.
