# Исследование: слой совместимости с ratatui поверх `gterm`

Дата: 2026-10-23. Вопрос владельца: можно ли (и как) сделать так, чтобы программы, написанные для консоли на ratatui, использовали `gterm` как графический бэкенд.

Источники (прочитаны, а не по памяти): `ratatui 0.30.2` и `ratatui-core 0.1.2` из реестра (`src/backend.rs`, `src/buffer/cell.rs`, `src/style.rs`, `src/style/color.rs`, `src/terminal/{buffers,cursor,init,resize}.rs`, `src/backend/test.rs`), `crossterm 0.29.0` (`src/event.rs`), `winit 0.30.13` (`event_loop.rs`, `application.rs`), код `gterm` (`app/{mod,api,events}.rs`, `buffer.rs`, `cell.rs`).

## 1. Что такое «бэкенд» в ratatui

Контракт — трейт `ratatui_core::backend::Backend` (ratatui 0.30 разделён на `ratatui-core` с трейтом и ядром и обёртки `ratatui-crossterm`/`-termion`/`-termwiz`):

| Метод | Что делает | Аналог в `gterm` |
|---|---|---|
| `draw(I)` где `I: Iterator<Item = (u16, u16, &Cell)>` | только **изменившиеся** ячейки (ratatui сам диффит два буфера) | `ScreenBuffer::set_cell(col, row, ch, fg, bg, flags)` — dirty-строки у `gterm` свои |
| `flush()` | вытолкнуть на экран | `Ctx::redraw()` / запрос перерисовки |
| `size()` → `Size { width, height }` | сетка в ячейках; вызывается перед **каждым** кадром (`autoresize`) | `screen.cols()/rows()`; `AutoGrid` меняет сетку при изменении окна |
| `window_size()` → ячейки + пиксели | необязательно, `0,0` допустимо | ячейка × метрики |
| `clear()`, `clear_region(ClearType)` | очистка всей области / до или после курсора | `clear_all`, `fill_rect` |
| `hide_cursor()/show_cursor()`, `get/set_cursor_position` | курсор терминала | у `gterm` курсора в библиотеке нет (ADR-0004) — слой рисует сам (обмен fg/bg или флаг) |
| `append_lines(n)` | только для `Viewport::Inline` | не нужен: окно — всегда `Fullscreen` |
| `scroll_region_up/down` | есть реализация по умолчанию | — |

Ячейка ratatui: `symbol: Option<CompactString>` (графемный кластер, **может занимать больше одной ячейки**), `fg`, `bg`, `underline_color: Color`, `modifier: Modifier`, `skip`. `Color`: `Reset`, 16 именованных, `Rgb(u8,u8,u8)`, `Indexed(u8)`. `Modifier`: `BOLD, DIM, ITALIC, UNDERLINED, SLOW_BLINK, RAPID_BLINK, REVERSED, HIDDEN, CROSSED_OUT`.

Эталонная реализация без терминала — `TestBackend` (буфер в памяти): по объёму ≈ 150 строк; наш бэкенд структурно такой же.

## 2. Сопоставление модели ячейки

| ratatui | `gterm` | Решение слоя |
|---|---|---|
| `symbol` — графема из 1+ кодовых точек, ширина 1 или 2 | `Cell::ch: char`, ширина всегда 1 | первая кодовая точка; комбинируемые знаки отбрасываются; **широкие (CJK, эмодзи) — одна ячейка**, ratatui при этом ставит `skip` на вторую — слой её очищает, иначе мусор |
| `Color::Rgb` | `Color::from_rgb` | прямое |
| `Color::Indexed(n)` | — | таблица xterm-256 (16 + куб 6×6×6 + 24 серых) в слое |
| 16 именованных + `Reset` | — | палитра слоя (настраиваемая), `Reset` → цвета по умолчанию `ScreenBuffer::default_colors` |
| `BOLD`, `ITALIC`, `UNDERLINED` | `CellFlags::BOLD/ITALIC/UNDERLINE` | прямое (`BOLD` у `gterm` ещё и осветляет цвет — так и в терминалах) |
| `REVERSED` | нет (`INVERSE` удалён, ADR-0012) | обмен fg/bg при записи ячейки — ровно так ТЗ §13 предписывает делать курсор |
| `DIM` | нет | затемнение fg в слое (×2/3) |
| `HIDDEN` | нет | fg := bg |
| `CROSSED_OUT`, `SLOW/RAPID_BLINK`, `underline_color` | нет | **теряются** (мигание в `gterm` принципиально нет — ADR-0012; зачёркивание и цвет подчёркивания — только новая функция рендерера) |

## 3. Главная проблема — кто владеет циклом событий

Приложение ratatui пишется так: `loop { terminal.draw(|f| ui(f))?; match crossterm::event::read()? { … } }` — **оно владеет циклом** и блокируется на чтении событий. `gterm::App::run` тоже владеет циклом (`winit`, главный поток, `ControlFlow::Wait`) и зовёт `AppHandler` по событиям. Два владельца цикла в одном потоке невозможны. Варианты:

**А. Два потока + мост (рекомендуется).** Главный поток — `gterm::App` (так требует `winit`). Приложение ratatui — во втором потоке, с бэкендом `GtermBackend`, который держит `Arc<Mutex<ScreenBuffer>>` (или свою копию буфера) и канал событий. Бэкенд при `flush` копирует ячейки в общий буфер и **будит** главный цикл; `AppHandler` слоя на `RedrawRequested` копирует общий буфер в `ctx.screen`, а события ввода (`on_key`, `on_text`, `on_pointer`, `on_grid_resized`) переводит в события для второго потока. Что нужно от `gterm`: **пробуждение цикла из другого потока** — сейчас его нет: `EventLoop::new()` без пользовательских событий, перерисовка только из колбэков. У `winit` это `EventLoop::with_user_event()` + `create_proxy()` + `ApplicationHandler::user_event` — изменение в `app/mod.rs`/`events.rs` (новый тип `Wake`/`AppProxy` с методом `request_redraw()`, `Send + Sync`). Объём — небольшой, но это новая публичная сущность и ADR.

**Б. Переписать приложение как `AppHandler`.** Без второго потока: `terminal.draw` вызывается из `on_redraw`/колбэков, события приходят в `on_key`. Совместимость «как для консоли» теряется: приложение меняет структуру. Годится только для новых программ.

**В. Эмуляция терминала (VT/PTY).** `gterm` становится настоящим терминалом с парсером ANSI (ТЗ §13 «VT/ANSI-парсер и PTY»), приложение запускается как дочерний процесс с crossterm-бэкендом — ноль изменений в приложениях, но это отдельный большой проект (парсер `vte`, PTY/ConPTY, ввод в escape-последовательностях), не слой совместимости.

## 4. Ввод: неустранимое ограничение «нулевых правок»

Приложения на ratatui читают события **напрямую из crossterm** (`crossterm::event::read/poll`) — ratatui событий не определяет. Перехватить `crossterm::event::read()` снаружи нельзя: он читает stdin/консольный ввод. Поэтому «программа для консоли без изменений» недостижима в варианте А: как минимум две правки в приложении — создать `Terminal::new(GtermBackend)` вместо `CrosstermBackend` и читать события из слоя вместо crossterm. Чтобы правка была минимальной, слой может отдавать события **в типах crossterm** (`crossterm::event::{Event, KeyEvent, KeyCode, KeyModifiers, MouseEvent}`) — тогда `match` в приложении не меняется. Цена — зависимость слоя от `crossterm` ради типов (у него есть фича-набор; под Windows он тянет `winapi`/`windows-sys` — размер и NFR-3 нужно замерить; альтернатива — свой enum, зеркальный crossterm, и `From` в обе стороны под фичей).

Перевод событий `winit` → crossterm: `KeyEvent { logical_key, text, state, repeat }` → `KeyCode` (Char/Enter/Esc/F(n)/стрелки/…) + `KeyModifiers` (нужно отслеживать состояние модификаторов — `winit` даёт `ModifiersChanged` отдельным событием, которого в `AppHandler` сейчас нет → ещё одно расширение `gterm`), `KeyEventKind::Press/Release`; `PointerEvent` → `MouseEvent` (координаты в пикселях → ячейки по метрикам; у `Ctx` их нет → слой должен знать размер ячейки: расширение `Ctx` или `on_grid_resized` + размер окна); `on_grid_resized` → `Event::Resize(cols, rows)`; `on_text` → `KeyCode::Char` для IME-ввода; `Paste` — нет буфера обмена в `gterm` (не входит).

## 5. Что ещё не ложится один в один

- **Размер сетки.** ratatui спрашивает `size()` перед каждым кадром и ждёт, что `draw` получит координаты в этой сетке; при `AutoGrid` сетка меняется в главном потоке при `Resized` — между `size()` и `draw` второго потока она может уже поменяться. Решение: бэкенд держит **свою** сетку (последнее `Resize`, доставленное приложению), общий буфер при расхождении пересобирается в главном потоке (`copy_region`, обрезка). Либо `FixedGrid`: окно не меняет сетку, приложение само запрашивает `Request::grid` — проще, но терминальное поведение «окно растянули — ratatui перерисовал под новый размер» теряется.
- **Курсор.** Слой рисует его обменом fg/bg поверх общего буфера на каждом кадре (ADR-0004, §13); мигания нет.
- **Производительность.** `draw` отдаёт только изменившиеся ячейки — ложится на dirty-строки `gterm`; копирование буфера 200×60 ячеек по 16 байт — 192 КБ на кадр в худшем случае, это не горячий путь рендера (NFR-6 про рендер, не про слой), но стоит копировать по строкам с dirty-флагами.
- **MSRV.** `ratatui-core 0.1.2` требует Rust 1.88, `gterm` объявляет 1.85. Слой как **отдельный крейт** workspace (`crates/gterm-ratatui`) с собственным `rust-version = "1.88"` не трогает MSRV библиотеки; как фича внутри `gterm` — поднял бы MSRV всем.
- **Зависимости.** `ratatui-core` тянет `compact_str`, `unicode-width`, `unicode-segmentation`, `bitflags`, `strum`, `itertools` и др. — в библиотеку `gterm` их тащить нельзя (§10.2), в отдельный крейт — нормально; `ratatui` целиком нужен только приложению.

## 6. Оценка

| Часть | Объём | Что трогает |
|---|---|---|
| Пробуждение цикла из другого потока (`AppProxy::request_redraw`) + `ModifiersChanged` в `AppHandler` + размер ячейки в `Ctx` | ≈ 150 строк | `gterm` (ADR, ТЗ FR-25/§5.2) |
| `GtermBackend: Backend` (буфер, диффы, курсор, палитра 16/256, модификаторы) | ≈ 250 строк + тесты на `TestBackend`-подобных сценариях | новый крейт `gterm-ratatui` |
| Мост потоков: общий буфер, канал событий, `AppHandler` слоя | ≈ 200 строк | новый крейт |
| Перевод событий `winit` → crossterm-типы | ≈ 250 строк (таблица клавиш) + тесты | новый крейт, фича `crossterm-events` |
| Пример: любой демо-пример ratatui (например, `demo2`) с двумя правками | ≈ 100 строк | `crates/gterm-ratatui/examples/` |

Итого порядка 1 000 строк с тестами и документами — одна задача по циклу TL с ТЗ, двумя-тремя ADR (пробуждение цикла; отдельный крейт и граница совместимости; палитра/модификаторы), примером и замером размера.

## 7. Вывод и рекомендация

1. Слой **реализуем**, и ratatui для этого спроектирован: трейт `Backend` мал, диффы ячеек отдаёт сам ratatui, `TestBackend` — готовый образец.
2. «Программа для консоли без правок» **невозможна** в варианте А: приложение владеет циклом и читает события из crossterm. Честная цель — **две правки в приложении**: другой бэкенд при создании `Terminal` и другой источник событий (с теми же crossterm-типами, чтобы `match` остался прежним). Полная прозрачность — только вариант В (терминал с VT/PTY), это другой проект.
3. Делать как **отдельный крейт `crates/gterm-ratatui`** (не фича `gterm`): свой MSRV 1.88 и зависимости `ratatui-core`, не меняет размер `demo.exe`; фича `crossterm-events` внутри него — за типы событий.
4. В самой `gterm` нужны три небольших расширения, полезные и без ratatui: пробуждение цикла из другого потока, событие смены модификаторов, размер ячейки в `Ctx`.
5. Теряются: мигание, зачёркивание, цвет подчёркивания, графемы шире одной ячейки (эмодзи и CJK займут одну ячейку), `Paste`, `Viewport::Inline`. Это предел модели `gterm` (одна кодовая точка на ячейку, нет таймера), не слоя.

Если решение «делать» — следующий шаг по TL-02: ТЗ `docs/spec/<дата>-ratatui-backend.md` с границами из §§2–5 и открытыми решениями: crossterm-типы событий против своего enum; `AutoGrid` против `FixedGrid` для сетки; какой пример ratatui брать для демонстрации.
