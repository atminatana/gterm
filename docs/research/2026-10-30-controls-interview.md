# Собранная картина: контролы с фокусом и событиями в `gterm-widgets` (перезапуск)

Дата: 2026-10-30. Итог интервью с владельцем (`/grillme`) после решения начать вопрос с чистого листа: решения интервью 2026-10-27 (`2026-10-27-focus-interview.md`), варианты В0–В5 (`2026-10-27-focus-models.md`) и черновик ТЗ `docs/spec/2026-10-27-widget-focus.md` помечены отклонёнными и в этом документе не используются. Черновик ТЗ по итогам — `docs/spec/2026-10-30-widget-controls.md`.

## Ключевые факты

- Виджеты части 1 — немедленный режим: `Widget::render(self, area, buf)` и `StatefulWidget::render(self, area, buf, state)`, состояние у приложения (`crates/gterm-widgets/src/widgets/mod.rs:21-28`; ADR-0023 п. 3). Ввод виджеты не обрабатывают.
- Фокус в примере — вручную: `enum Focus { List, Table }` и `match` по клавишам в приложении (`examples/widgets.rs:101-105, 233-257`).
- `gterm` отдаёт `on_key(&KeyEvent)` только для нажатий (`app/events.rs:38`), без модификаторов — `WindowEvent::ModifiersChanged` в `events.rs` не обрабатывается (grep по файлу); `on_pointer` — физические пиксели в `Moved`, кнопки и колесо без координат (`app/api.rs:17-32`); `Ctx` — экран, запросы, статистика, без размера ячейки (`api.rs:72-79`). Размер ячейки внутри библиотеки уже есть — `pub(super) fn cell_px` (`app/window.rs:17-22`).
- `Popup` — прямоугольник на сетке плюс прозрачный буфер наложения с фоном по альфе, без ввода (`widgets/popup.rs`).
- ADR-0004: типы `winit` не переводятся, `Esc` не перехватывается; ТЗ §13: ввод и курсор — на стороне приложения.
- `winit` у `gterm-widgets` только в `dev-dependencies` (`crates/gterm-widgets/Cargo.toml`).

## Решения пользователя

1. **Цель** — конкретное приложение на `gterm` класса «панели и диалоги» (файл-менеджер). Его требования первичны; библиотека виджетов — средство для него.
2. **Форма кода** — приложение описывает экран один раз функцией `ui()` из ссылок на свои состояния; крейт раскладывает, рисует и маршрутизирует ввод; приложение получает смысловые события. Отклонены: контролы-объекты с ручной маршрутизацией в приложении; долгоживущее дерево объектов в духе Turbo Vision.
3. **Свои контролы и составные из встроенных одинаково важны**; механизм обязан поддерживать оба пути без особых случаев. Свой контрол — тип приложения, реализующий трейт крейта.
4. **Сообщения как в iced, оба пути**: встроенные контролы получают сообщение при описании в `ui()`; свой контрол знает тип сообщений приложения и публикует сам из обработчика. Приложение разбирает сообщения в одном месте после маршрутизации.
5. **Маршрутизация возвращает только «обработано или нет»**. Адрес контрола в событии (ссылка, идентификатор) — задел на будущее, сейчас не требуется.
6. **Мышь базовая**: клик даёт фокус и выбор, колесо крутит; координаты в индексах ячеек, текущая ячейка — в самих событиях. Двойной клик и перетаскивание — позже, механизм не должен им мешать.
7. **Граница `gterm`**: добавить ячейку под указателем в события мыши, модификаторы и размер ячейки в `Ctx`; типы `winit` остаются (ADR-0004 по духу соблюдён). Отклонены: перевод только в крейте виджетов; пересмотр контракта ввода целиком.
8. **Слои первого шага** — основной экран и модальный диалог как часть того же описания `ui()`; механизм отдаёт весь ввод верхнему модальному слою и рисует оба. Меню, подсказки, немодальные окна — позже, без противоречия механизму.
9. **Глобальные клавиши** (F5, F10, Alt+F1) — приложение разбирает необработанное деревом; в модальном диалоге они до приложения не доходят. Карта «сочетание → сообщение» в описании экрана — не сейчас.
10. **Объём первого шага** — механизм, кнопка, фокус и клавиши у существующих списка и таблицы, модальный слой. Поле ввода (командная строка) и выпадающий список — следующие задачи на готовом механизме.
11. **Tab** — контейнеры описания прозрачны: фокус берут только контролы-листья, обход в порядке объявления в глубину по кольцу; свой контрол для механизма — одна единица фокуса.
12. **Из рисков pre-mortem** реальны три: много ручного кода в приложении, слишком сложная абстракция, невозможность написать свой контрол. Отличия поведения от привычных UI волнуют меньше всего.

## Допущения

- `ui()` строится заново на каждое событие и кадр из `&mut` на состояния приложения; сообщения применяются после разбора дерева, как `update(msg)` в iced — предположение по выбранному эскизу кода и аналогии; в ТЗ зафиксировано как контракт порядка вызовов.
- Клик вне модального диалога поглощается — предположение; в ТЗ открытый вопрос.
- Контейнер с рамкой может подсвечивать её, когда фокус внутри — предположение из описания варианта, не отдельное решение.
- Состояния встроенных контролов остаются у приложения, виджеты потребляются при отрисовке — проверено (ADR-0023 п. 3).

## Риски и митигация

- Риск: дерево держит `&mut` на все состояния, пока живёт; сообщение нельзя применить «во время» → Митигация: порядок «маршрутизация → сброс дерева → разбор сообщений → `ui().render()`» в контрактах ТЗ и в примере.
- Риск: тип сообщения как параметр механизма тянет обобщения через крейт → Митигация: эскиз сигнатур трейта контрола и описания экрана — в плане; проверка компилируемости на минимальном примере до основной работы.
- Риск: правка публичного `PointerEvent` ломает демо и оконные тесты → Митигация: поля добавляются, не убираются; список затронутых мест — в плане.
- Риск: повторение истории первого ТЗ (переписано дважды) → Митигация: ТЗ описывает контракт и критерии приёмки, не внутреннее устройство; устройство — в плане и ADR после утверждения.

## Открытые вопросы — закрыты владельцем 2026-10-30 (ТЗ §6)

- Публикация из своего контрола — `&mut` очередь сообщений аргументом обработчика; возврат `Option<Msg>` отклонён.
- Клик вне модального диалога — поглощается; привязка «клик мимо» отложена до меню.
- `Popup` остаётся с тем же API в `widgets/popup.rs`, модальный слой использует его внутри, логика слоя — в отдельном файле.
- Кнопка активируется по отпусканию внутри области после нажатия в ней; захват указателя между нажатием и отпусканием входит в первый шаг.
- `Esc` в модальном слое — необязательная привязка `on_escape(Msg)` у слоя; без неё — необработанное приложению.
