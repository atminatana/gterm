# Собранная картина: фокус, события и фреймы в `gterm-widgets`


> **Отклонено 2026-10-30.** Владелец решил начать вопрос с чистого листа; решения ниже отменены и в новом обсуждении не используются.

Дата: 2026-10-27. Итог интервью с владельцем по постановке «фокус в контролах» (`/grillme`). Разбор вариантов — `docs/research/2026-10-27-focus-models.md`; черновик ТЗ до интервью — `docs/spec/2026-10-27-widget-focus.md` (описывает вариант В4, подлежит переписи под решения ниже).

## Ключевые факты

- Виджеты части 1 — немедленный режим: виджет потребляется `render(self, area, buf[, state])`, состояние у приложения (`crates/gterm-widgets/src/widgets/mod.rs:21-28`, `list.rs:44-47`). Ввод виджеты не обрабатывают; фокус в примере — `enum Focus` и `match` в приложении (`examples/widgets.rs:101-105, 233-257`).
- `Popup` — прямоугольник на сетке и буфер наложения с фоном по альфе, рисуется в `on_redraw` через `DrawCtx::draw_buffer` (`widgets/popup.rs`).
- `gterm` не отслеживает модификаторы (`WindowEvent::ModifiersChanged` в `app/events.rs` не обрабатывается — `grep` по `crates/gterm/src` пуст), `PointerEvent::Moved` в физических пикселях, `Input` без координат, `Ctx` без размера ячейки (`app/api.rs:17-32, 72-79`). Без `Ctx::modifiers` нет `Shift+Tab`; без `Ctx::cell_px` нет координат в ячейках.
- ratatui (`ratatui-widgets 0.3.2`, реестр cargo): фокуса и событий нет, `ListState` даёт только `select_next`/`select_previous`/`scroll_*`, вызываемые приложением.
- iced (`iced_core`, github master): фокус в состоянии каждого виджета (`Focusable { is_focused, focus, unfocus }`), `Tab` — обход дерева со счётчиком `Count { focused, total }` и установкой по индексу, без цикла; событие спускается всем детям, принявший зовёт `shell.capture_event()`; сообщения — `shell.publish`; `Id` только для адресации извне; дерево пересобирается на каждый `view()`.

## Решения пользователя (2026-10-27, кандидаты в ADR)

1. **Модель В2+.** Фокус и область — поля состояний виджетов (`focused: bool`, `area: Rect` в `ListState`, `TableState`, новых `ButtonState`, `GroupState`); обработка ввода — трейт `Node` на состояниях; структура экрана описывается один раз методом `tree()`, возвращающим временное дерево ссылок `&mut` на состояния вместе с виджетами-значениями и `Layout` групп. Это же дерево раскладывает (`layout(area)`), рисует (`render(buf)`, потребляя виджеты, как в ADR-0023) и маршрутизирует ввод (`route_key`, `route_mouse`, `focus_next`/`focus_prev`). Без `Id`, без `Box<dyn>` в хранении, без пересборки состояния; дерево ссылок строится на событие и на кадр.
2. **События.** Общий `enum Event` крейта (`Selected(usize)`, `Activated`, `Changed`, `Close`, …) с адресацией путём индексов в дереве; `Response { handled: Handled, event: Option<Event> }`. Типизированные по контролу события (вариант В3) отклонены в пользу простоты.
3. **Диалог закрывается событием.** Непринятый `Esc` или `Activated` от кнопки «OK/Отмена» фрейм превращает в `Event::Close`; приложение убирает диалог. `Esc` при этом не перехватывается `gterm` (ADR-0004 соблюдён).
4. **Объём задачи:** механизм (фокус, маршрутизация, фреймы, адаптеры списка и таблицы, группа) **плюс простейшая кнопка** (`Enter`/пробел/клик → `Activated`). Чекбокс, поле ввода, выпадающий список, карта сочетаний клавиш — отдельные задачи из `TODO.md`.
5. **Фрейм диалога — через наложение, как `Popup`:** буфер с непрозрачным фоном и полупрозрачной тенью (`dx = 2, dy = 1`, чёрный с альфой) кладётся в `on_redraw` через `draw_buffer`; дерево диалога строится там же для отрисовки и в обработчиках для маршрутизации. `Popup` заменяется `Frame`.
6. **Мышь вне модального диалога:** событие поглощается, главный экран ввода не получает, диалог остаётся; приложение видит `Handled::No`.
7. Ранее (постановка 2026-10-27): `Tab`/`Shift+Tab` по циклу; у вложенных `focusable` фокус уходит с родителя после последнего дочернего; левая кнопка на `focusable` даёт фокус; координаты мыши в ячейках.

## Допущения

- Группа (`GroupState`) по умолчанию клавиши не обрабатывает (`Handled::No`); контейнер с собственной обработкой — свой тип состояния с `impl Node`. `предположение`
- Необработанная мышь поднимается к родителю так же, как клавиатура (О4 черновика ТЗ). `предположение`, владелец не возражал
- Порядок узлов в `tree()` = порядок отрисовки = порядок попадания мыши (последний — верхний). `следует из В2+`
- Расширения `gterm`: `Ctx::modifiers`, `Ctx::cell_px`; положение указателя между `Moved` и `Input` запоминает крейт виджетов. `проверено (api.rs), решение не оспорено`
- Тест К2 ADR-0023 (рендер виджетов части 1) не меняет ожиданий: `focus_style` применяется только при `state.focused == true`. `предположение`

## Риски и митигация

- Риск: пока дерево ссылок живёт, все состояния заняты `&mut`; приложение не может читать `self.list.selected()` «во время». → Митигация: разбирать `Response`/событие после сброса дерева; в примере показать порядок «route → разобрать → tree().layout().render()».
- Риск: `GroupState` для `Block` — новое состояние у виджета, который был `Widget` без состояния. → Митигация: `Block` остаётся `Widget`; `Tree::group` сам рисует `Block` со стилем из `GroupState`, не меняя `Block::render`.
- Риск: дерево строится на каждый кадр с `Vec` узлов — выделения в обработчиках. → Не затрагивает NFR-6 (рендерер); замерить в `--bench`-подобном сценарии не требуется, но размер `widgets.exe` записать (NFR-1).
- Риск: фокус остаётся на узле, который пропал из `tree()` (условный виджет) или стал `enabled == false`. → Митигация: `route_*`/`focus_next` при отсутствии узла с `focused` ведут себя как при `None`; состояние пропавшего узла сохраняет `focused = true`, но крейт его не видит — задокументировать, добавить тест.
- Риск: два дерева (главное и диалога) при открытом диалоге. → Митигация: `Modal`-помощник крейта: `route` идёт диалогу, если он есть; главное дерево не маршрутизируется, его флаги фокуса не трогаются — восстанавливать нечего.
- Риск: `winit` как обычная зависимость `gterm-widgets` (типы `KeyEvent`, `ModifiersState`, `MouseButton`). → Те же фичи, что у `gterm`, новых транзитивных зависимостей нет; замерить размер.

## Открытые вопросы

- Нужна ли группе собственная обработка клавиш уже в этой задаче (например, `Enter` в группе = активировать кнопку по умолчанию) — сейчас допущение «нет».
- Колесо мыши над не фокусируемым узлом (абзац): поднимать к родителю или игнорировать — сейчас «поднимать» по О4.
- Двойной клик — не входит; подтвердить при ТЗ на поле ввода/список.
