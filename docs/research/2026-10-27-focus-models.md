# Исследование: модели фокуса и событий для контролов `gterm-widgets`


> **Отклонено 2026-10-30.** Владелец решил начать вопрос с чистого листа; варианты и оценки ниже — история, в новом обсуждении не используются.

Дата: 2026-10-27. Вопрос владельца: как реализовать контролы с фокусом и событиями так, чтобы реализация была простой, идиоматичной для Rust, структура экрана описывалась в одном месте, и при этом выполнялась постановка (`focusable`/`focused`, клавиатура — фокусу с подъёмом к родителю, мышь — верхнему под указателем в координатах ячеек, `Tab`/`Shift+Tab` по циклу с правилом для вложенных, модальные фреймы). Предпочтение владельца — варианты, близкие к рендеру ratatui плюс отдельный компонент фокуса; идентификаторы виджетов (`Id`) и пересборка дерева на каждый кадр нежелательны.

Источники (прочитаны, а не по памяти): код `crates/gterm-widgets/src/widgets/{mod,list,popup}.rs`, `examples/widgets.rs`, `crates/gterm/src/app/{api,events}.rs`; `ratatui-widgets 0.3.2` и `ratatui-core 0.1.2` из реестра cargo; iced — `core/src/widget/operation/focusable.rs`, `core/src/shell.rs`, `widget/src/text_input.rs` (github, master) и docs.rs `iced_core::Widget`; `docs/research/2026-10-23-ratatui-backend.md` §4; черновик ТЗ `docs/spec/2026-10-27-widget-focus.md`.

## 1. Точка отсчёта — что есть сейчас

- Виджет — значение, потребляемое `render(self, area, buf)`; состояние (`ListState { offset, selected }`) — у приложения (`widgets/mod.rs:19-28`, `list.rs:43-47`). Ввод виджеты не обрабатывают.
- Фокус в примере — `enum Focus { List, Table }` и `match` в `on_key` (`examples/widgets.rs:101-105, 233-257`): приложение само решает, кому отдать стрелки и какую рамку подсветить.
- `Popup` — прямоугольник на сетке плюс буфер наложения с фоном по альфе (`popup.rs`).
- `gterm` отдаёт `on_key(&KeyEvent)` без модификаторов (`ModifiersChanged` в `app/events.rs` не обрабатывается — `grep` пуст) и `on_pointer` с физическими пикселями; `MouseInput` без координат, размер ячейки в `Ctx` не отдаётся (`api.rs:15-32, 71-79`). Эти три расширения `gterm` (модификаторы, `cell_px`, запоминание положения указателя) нужны **любому** варианту ниже и дальше не повторяются.

## 2. Как это сделано в ratatui и iced

**ratatui** (`ratatui-widgets 0.3.2`): фокуса и событий нет вообще. В исходниках виджетов слово «focus» встречается один раз в комментарии; `ListState` даёт `select_next`/`select_previous`/`scroll_down_by`/`scroll_up_by`, которые приложение вызывает из своего `match` по событиям crossterm. Все решения о фокусе — у приложения; ratatui — это ровно сегодняшний пример.

**iced** (`iced_core`): дерево виджетов пересобирается на каждый `view()` из состояния приложения; внутреннее состояние виджетов живёт в отдельном дереве `Tree`, сопоставляемом по `tag`/`diff`. События: `Widget::update(tree, event, layout, cursor, renderer, clipboard, shell, viewport)` — событие спускается от корня ко всем детям по порядку; принявший зовёт `shell.capture_event()` («Prevents event bubbling»), наружу — `shell.publish(message)`. Фокус — в состоянии каждого виджета (`trait Focusable { is_focused, focus, unfocus }`); `Tab` — операция обхода: `Count { focused: Option<usize>, total }` считает фокусируемые в порядке обхода, затем вторая операция ставит фокус по индексу; `focus_next` без цикла; адресный фокус — `operation::focus(Id)`, `Id` необязателен. Мышь: центрального попадания нет, каждый виджет сам проверяет `cursor.is_over(bounds)`.

Вывод для нас: «фокус как состояние самого контрола» и «обход по порядку структуры» — общая практика; `Id` в iced нужен только для адресации извне и для сопоставления пересобранного дерева. Если дерево не пересобирать, `Id` не нужен.

## 3. Критерии сравнения

| Код | Критерий | Что считаем |
|---|---|---|
| П | Простота реализации | строк в крейте; строк в приложении на экран из примера (список, таблица, абзац, диалог с кнопкой) |
| И | Идиоматичность Rust | владение в одном месте, без `Rc<RefCell>`, минимум `dyn`/`Box`, типы проверяет компилятор |
| С | Структура в одном месте | порядок обхода, вложенность и раскладка описаны один раз, а не отдельно в `draw` и в `on_key` |
| Ф | Постановка по фокусу | `focusable`/`focused` через потомка, `Tab` по циклу с правилом «с родителя после последнего дочернего» |
| К | Клавиатура | фокусу, `Handled`, подъём к родителю до фрейма |
| М | Мышь | верхний под указателем, фокус по левой кнопке, захват, ячейки |
| Е | События | как приложение узнаёт «выбран пункт 3 в списке слева» |
| Д | Модальность | диалог получает весь ввод, фокус под ним сохраняется |
| − | Без `Id` и без пересборки | требования владельца |

## 4. Варианты

Нумерация — по удалённости от ratatui: В0 ближе всего.

### В0. Как сейчас: ratatui-рендер, `match` в приложении

Ничего не добавляется. Приложение хранит `enum Focus`, в `on_key` делает `match`, в `draw` подсвечивает рамки по `self.focus`.

- П: крейт 0 строк; приложение — `enum` + два `match` на каждый экран, растёт линейно с числом контролов, диалог — ещё один `enum` и условие «если диалог открыт».
- И: образцово — всё владеет приложение. С: нет — структура размазана по `draw` и `on_key`. Ф/К/М/Д: всё вручную, крейт ничего не гарантирует. Е: не нужны — приложение само меняет своё состояние.
- Это ratatui. Годится как базовая линия, постановку не выполняет.

### В1. ratatui-рендер + `FocusControl` по регистрации прямоугольников

Идея egui: при отрисовке виджет (или приложение) регистрирует «фокусируемый прямоугольник» в `FocusControl`: `focus.register(area, parent_depth)`. Порядок регистрации — порядок обхода, глубина — вложенность. `FocusControl` хранит индекс текущего фокуса и список прямоугольников прошлого кадра; `Tab` — индекс ± 1 по циклу; мышь — последний зарегистрированный прямоугольник, содержащий точку.

```rust
// draw
let mut f = self.focus.begin();          // очищает список
f.group(outer_rect, |f| {                // вложенность — замыкание
    StatefulWidget::render(list.focused(f.register(left)), left, buf, &mut self.list);
    StatefulWidget::render(table.focused(f.register(top)), top, buf, &mut self.table);
});
// on_key
match self.focus.current() { Some(0) => self.list.handle(key), Some(1) => self.table.handle(key), _ => {} }
```

- П: крейт ≈ 150 строк (список прямоугольников, обход, попадание). Приложение: регистрация в `draw` и всё тот же `match` по **индексу** в `on_key`.
- И: нормально, без `dyn`. С: нет — порядок задаётся в `draw`, а обработка клавиш сопоставляется с ним по числу; условно отрисованный виджет сдвигает индексы — классическая ошибка этой схемы, в egui её закрывают `Id`.
- Ф: `Tab` по циклу есть; «родитель после последнего дочернего» — через глубину, реализуемо. `focused` у контейнера — по глубине, реализуемо. К: подъёма нет — крейт не знает обработчиков. М: верхний под указателем есть, фокус по клику есть, захват — да. Е: не нужны. Д: диалог — второй `FocusControl`, переключение вручную.
- Вывод: дешёвый обход и попадание, но обработка клавиш остаётся `match`-ем по индексам, и структура описана в `draw`, а не в одном месте. Хрупко.

### В2. ratatui-рендер + состояния с фокусом + `FocusControl` над деревом ссылок

Ближайший к ratatui вариант, выполняющий постановку. Три идеи:

1. **Фокус и область — в состоянии виджета** (как `Focusable` в iced). `ListState`, `TableState`, новые `ButtonState`, `GroupState` получают поля `focused: bool`, `area: Rect` (область записывает `StatefulWidget::render` — одна строка в каждом виджете; для `Block` появляется `GroupState`, которому `Block::render_stateful` отдаёт область и из которого берёт `focused`). Отрисовка остаётся ratatui-стилем: `List::new(..).block(Block::bordered().focus_style(..))`; «подсветить при фокусе» делает сам виджет по `state.focused`.

2. **Обработка ввода — трейт на состоянии**, не на виджете: `trait Node { fn focusable(&self) -> bool; fn area(&self) -> Rect; fn focused(&mut self) -> &mut bool; fn on_key(&mut self, &KeyMsg) -> Response; fn on_mouse(&mut self, &MouseMsg) -> Response; }`. `ListState::on_key` знает стрелки/`Home`/`End`/`PgUp`/`PgDn`, `on_mouse` — клик по пункту и колесо; `ButtonState` — `Enter`/пробел/клик → `Activated`. Это небольшое расширение существующих типов состояний, а не новая иерархия.

3. **Структура описана один раз — методом, отдающим дерево ссылок:**

```rust
impl Demo {
    fn tree(&mut self) -> Tree<'_> {
        Tree::group(&mut self.left_group, [
            Tree::leaf(&mut self.list),
        ])
        .then(Tree::group(&mut self.right_group, [
            Tree::leaf(&mut self.table),
            Tree::leaf(&mut self.ok_button),
        ]))
    }
}
```

`Tree<'a>` — временная структура из `&'a mut dyn Node` (вектор узлов с индексом родителя или вложенные массивы). Она строится **на событие**, не на кадр, стоит несколько ссылок и одно-два выделения размером с число контролов; дерево виджетов и состояние не пересобираются. `FocusControl` — набор свободных функций над `Tree`: `focus_next(&mut tree)`, `focus_prev`, `route_key(&mut tree, msg) -> Response`, `route_mouse(&mut tree, msg) -> Response`, `focus_at(&mut tree, col, row)`. Текущий фокус — тот узел, у которого `focused == true` (инвариант: не больше одного листа; `GroupState.focused` = «внутри есть фокус», выставляется при маршрутизации).

Как закрываются требования:

- Ф: обход — по порядку узлов `Tree` в глубину (родитель, дети, следующий брат), цикл — замыкание на корне; `focusable` группы = `GroupState::focusable`. «Родитель после последнего дочернего» — свойство обхода в глубину. `focused` у группы — флаг, который `route`/`focus_next` ставит всем предкам листа.
- К: `route_key` находит лист с `focused`, зовёт `on_key`; при `No` — поднимается по индексу родителя, зовёт `GroupState::on_key` (по умолчанию `No`; приложение может завести свой тип группы с обработчиком); непринятое корнем возвращается приложению. `Tab`/`Shift+Tab` — до маршрутизации, кроме `wants_tab()`.
- М: `route_mouse` ищет последний узел, чей `area` содержит точку (порядок узлов = порядок отрисовки, если `tree()` перечисляет их в том же порядке, что `draw` — это обязанность приложения, легко нарушить; снимается тем, что `draw` тоже можно вести по `tree()`, см. ниже). Левая кнопка на `focusable` — снять старый флаг, поставить новый и предкам. Захват — поле `captured: Option<usize>`… но `Tree` временный, поэтому захват хранится как «в каком состоянии флаг `captured`» — ещё один `bool` в `Node`.
- Е: `Response { handled, event: Option<Event> }`, где `Event` — **одно перечисление крейта** (`Selected(usize)`, `Activated`, `Changed`, `Close`), потому что узлы в `Tree` — `dyn Node` и типизировать по узлу нельзя. «Какой список» приложение узнаёт по пути: `route_key` возвращает `(Response, path: &[usize])` либо приложение сравнивает `self.list.focused`. Это слабее типизированных событий В3, но для `match (path[0], event)` достаточно.
- Д: диалог — второй набор состояний и второй `tree()`; `Modal` в крейте — функция `route(&mut dialog_tree_or_main)`: если диалог открыт, маршрутизируем его дерево, иначе главное. Фокус главного дерева лежит во флагах его состояний и не трогается — восстанавливать нечего.
- −: `Id` нет (адрес — путь индексов в текущем дереве, его никто не хранит между событиями); пересборки виджетов нет; пересобирается только дерево ссылок на событие.

Рисование: остаётся ratatui-стилем в `draw`, как сейчас. Дублирование структуры (`draw` рисует в одном порядке, `tree()` перечисляет в другом) — главный риск варианта; его снимает приём «`draw` тоже вызывает `tree()`»: `Tree` умеет `render(buf)`, если узлы умеют рисовать себя — но тогда `Node` должен владеть и данными виджета (пункты списка), и это уже В3. Честный компромисс: `tree()` — единственное место порядка **обхода и попадания**, `draw` — единственное место **раскладки и вида**; расхождение ловится тестом «area из состояний после `draw` совпадает с порядком `tree()`» только частично.

**В2+ — `tree()` и рисует.** Вопрос владельца 2026-10-27: можно ли использовать то же дерево для отрисовки. Можно, если лист несёт не только состояние, но и виджет, а группа — `Block` и `Layout`:

```rust
fn tree(&mut self) -> Tree<'_> {
    Tree::group(&mut self.left, Block::bordered().title(" Список "), Layout::vertical([Fill(1)]), [
        Tree::leaf(&mut self.list, List::new(ITEMS).highlight_symbol("▶ ")),
    ])
    .then(Tree::group(&mut self.right, Block::bordered(), Layout::vertical([Length(11), Fill(1)]), [
        Tree::leaf(&mut self.table, Table::new(rows(), widths())),
        Tree::leaf(&mut self.ok, Button::new("OK")),
    ]))
}
// draw:    self.tree().layout(area).render(buf)
// on_key:  let mut t = self.tree(); let r = route_key(&mut t, &msg); t.layout(area).render(ctx.screen);
```

`layout` раздаёт `Rect` по `Layout` групп и записывает `area` в состояния; `render` потребляет дерево: рамка группы со стилем фокуса по `state.focused`, затем дети по порядку. Виджеты по-прежнему значения, потребляемые один раз (ADR-0023). Порядок обхода, отрисовки и попадания мыши — один по построению, тест на согласованность не нужен; `draw` приложения — одна строка; структура — в одном месте. Это `view()` из iced без `Id` и без `diff`: дерево держит прямые `&mut` на состояния, сопоставлять нечего.

Цена В2+: дерево ссылок и виджеты-значения создаются на каждый проход (как `List::new(ITEMS)` в `draw` сегодня) — `Vec` узлов на проход; лишнего прохода нет, так как в `on_key` доступны и событие, и `ctx.screen`, и одно дерево обслуживает маршрутизацию и отрисовку. Пока дерево живёт, все состояния заняты `&mut` — приложение разбирает событие до или после, не во время. `List`/`Table`/`Block` получают стиль фокуса из состояния (`focus_style`, небольшое расширение). Объём крейта — как у В2 плюс ≈ 100 строк на `layout`/`render` дерева.

- П: крейт ≈ 400–500 строк (`Node`, `Tree`, обход, маршрутизация, `GroupState`, расширение четырёх состояний, `ButtonState`) + тесты; приложение из примера ≈ 60 строк на `tree()`, `draw`, разбор событий — меньше, чем сегодняшний `match`, и не растёт с числом контролов.
- И: хорошо — состояние и данные у приложения, виджеты как были; `dyn Node` временный, без `Box`, без `Rc`. `&mut` на несколько полей одной структуры в `tree()` — компилятор разрешает, пока поля разные.
- С: обход, вложенность и события — в `tree()`; раскладка и вид — в `draw`. Два места, но с разной ответственностью.

### В3. Статическое дерево из кортежей, фокус индексом в контейнере

Контрол — тип в полях приложения, владеющий и состоянием, и данными (пункты списка). Контейнер `Group<C: Children>` держит детей кортежем, `focus: Focus::{None, Self_, Child(usize)}`, `captured: Option<usize>`, `Layout` для раскладки детей. `Children` реализован макросом для кортежей до 12 элементов. События типизированы на уровне типа: `type Event` у каждого контрола, у кортежа — `Child2<A, B>`/`Child3<…>`. Модальность — `Modal<M, D> { main, dialog: Option<D> }`. Полный эскиз сигнатур и алгоритмов `focus_next`/`on_key`/`on_mouse` — в переписке 2026-10-27 и переносится в ТЗ при выборе варианта.

- Ф/К/М/Д: закрывается полностью и локально: контейнер знает только индекс своего фокуса; подъём — возврат `No` по цепочке `Child(k)`; верхний под указателем — последний ребёнок с попаданием; «родитель после последнего дочернего» — `focus_next` контейнера возвращает `false`, пройдя последнего ребёнка.
- Е: самые сильные — тип события говорит, какой контрол его породил; `map` в свой `enum`, как `Element::map` в iced.
- С: да — дерево, порядок, раскладка и обработчики описаны одним типом в одном поле; `draw` сводится к `ui.render(buf)`.
- −: без `Id`, без пересборки, без `Box` (но `dyn` допустим, если захочется переменного числа детей).
- П: крейт ≈ 700–900 строк (трейт, `Group`, макрос кортежей, `Frame`, `Modal`, адаптеры `ListCtl`/`TableCtl`/`Label`/`Button`) + тесты; приложение ≈ 40 строк, но тип `Modal<Frame<Group<(ListCtl, Group<(TableCtl, Label)>)>>, Frame<…>>` пишется явно.
- И: идиоматично в смысле владения (нет `Rc`, нет `Box`), но макрос на кортежи и длинные типы — «тяжёлая» идиоматика; контролы владеют данными, а не заимствуют на кадр, поэтому ratatui-виджеты становятся внутренним слоем рисования.
- Риск: самый большой объём из вариантов без `Box`; немедленный режим ADR-0023 остаётся публичным, но перестаёт быть основным.

### В4. Удерживаемое дерево `Box<dyn Control>` в арене с `NodeId`

Вариант черновика ТЗ: `Frame` владеет `Vec<Node { control: Box<dyn Control>, parent, area }>`, `FocusManager` хранит `NodeId`, события — очередь. Доступ к состоянию — события или downcast.

- Ф/К/М/Д: всё закрывается, алгоритмы — проходы по вектору.
- С: да, дерево строится один раз в одном месте.
- И: слабее всех — `Box<dyn>`, индексы вместо типов, downcast либо «второй источник правды» (данные приложения и состояние контрола расходятся).
- −: `NodeId` — это `Id`, пусть и выданный крейтом; пересборки нет.
- П: ≈ 600–800 строк; приложение хранит `NodeId` и разбирает очередь.
- Владелец отклонил `Id`; вариант оставлен для полноты.

### В5. Пересборка дерева на проход (Elm/iced) со стабильными `Id`

Состояние у приложения, дерево адаптеров строится на каждое событие и на каждый кадр, фокус — по `Id`, события — возвращаемые значения. Отклонён владельцем: `Id` и пересборка. Для полноты: самый близкий к iced, ≈ 500 строк, идиоматичен, но платит пересборкой на каждое событие и ручными `Id`.

## 6. Оценка

- **В2** — лучший баланс под критерии владельца «просто, идиоматично, близко к ratatui»: виджеты и `draw` остаются как есть, добавляются два поля в состояния и трейт на них, обход и маршрутизация — свободные функции над временным деревом ссылок. Платит за это общим `enum` событий с путём вместо типизированных, и тем, что порядок в `tree()` и в `draw` — два места (с разной ответственностью). Подъём к родителю работает, но группа по умолчанию ничего не обрабатывает; свои обработчики у контейнера — через собственный тип группы.
- **В3** — полностью выполняет постановку и даёт лучшие события и «структура в одном месте», но это другой стиль крейта (контролы владеют данными), вдвое больше кода и тяжёлые типы. Выбирать, если формы с десятками контролов и вложенными диалогами — основной сценарий, а не демо.
- В1 дёшев, но хрупок; В0 — текущее состояние; В4/В5 — против требований владельца.

Два вопроса, которые решают выбор между В2 и В3:
1. Приемлем ли общий `enum Event` крейта с адресацией «путь индексов» вместо типизированных событий по контролу?
2. Что считать одним местом: В2 (обход — `tree()`, вид и раскладка — `draw`, два места с тестом согласованности) или В2+ (`tree()` несёт виджеты и `Layout`, рисует и маршрутизирует; дерево ссылок строится и на кадр)?

Ответ владельца 2026-10-27 на вопрос 1: общий `enum` + путь приемлем — В2/В2+. Вопрос 2: В2+ (решение 1 интервью, `2026-10-27-focus-interview.md`; подтверждено 2026-10-28) — ТЗ переписано под него.
